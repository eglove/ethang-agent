## What This Project Is

eThang Agent is an AI agent harness built with .NET, delivered through an Avalonia desktop application. The project follows strict Domain-Driven Design: layered bounded contexts, Specification patterns, and CQRS.

> **Read [`README.md`](README.md) first** — it carries the high-level overview and usage instructions. Whenever a change makes either stale, update the README in the same change.

## Guiding Philosophy

These principles explain every convention below. When a rule seems arbitrary, it traces back to one of these.

- **Seams over commitments.** Every external dependency — AI provider, shell, file system, UI — sits behind an interface the domain owns. Nothing external is ever allowed to become load-bearing inside a domain. Any implementation behind a seam must be replaceable without touching domain code.
- **Strict correctness at the boundaries.** Inputs crossing into the domain are validated completely: required parameters are required, types are exact, unknown input is rejected, and nothing is silently coerced, defaulted, or clamped. Deliberate exceptions exist but are named, documented decisions, never defaults — each proves the rule: (1) a benign overshoot that is clamped with a visible warning; (2) a nested exec-script tool call that omits timeoutSeconds inherits the enclosing exec call’s budget (restating the budget per nested call cost real sessions repeated failures; explicit nested values still win and are still validated; the inherited budget is INJECTED only into actions whose contract declares timeoutSeconds, and STRIPPED from the rest — so every ITool-backed action must declare the parameter, guarded by a composition-level invariant test — and an exec run that completes with empty output while nested calls ran is annotated with a discarded-result hint; a program that references Directory.GetCurrentDirectory() carries a workspace-note annotation stating the launch directory and the workspace root, because the two differ and scripts that confuse them silently read the wrong directory).
- **Errors are information, not crashes.** Expected failures flow through `Result<T>` / error values and are delivered to whoever can act on them — including the model itself, which receives tool errors as tool results so it can self-correct. Exceptions are reserved for programmer error.
- **Reversibility by construction.** The architecture must not preclude alternative frontends, platforms, providers, storage engines, or orchestration topologies. When a choice would foreclose an option, choose the seam instead.
- **The codebase is not the standard.** Existing code records what was done, not what is right. Never treat a current pattern as best practice just because it is present — when work touches code and a better way exists, improve it in the same change. Improve what you touch; do not launch unrelated refactors.
- **Lean, event-driven operations.** Aim for high performance and a small memory footprint. Prefer event-driven designs — react to what happened instead of polling, stream instead of loading, and don't hold what you're not using.
- **Direction: a self-contained agent.** The long-range shape (per the grand plan's philosophy, not its plan details) is a persistent desktop application that manages its own world — conversations, sessions, state, configuration — in app-owned structured storage rather than scattered project-level files. Work written today must fit that destination: durable state flows through domain-owned stores, never ad-hoc files.

## Architecture Principles

### Domain-Driven Design

The codebase is organized around business domains, not technical concerns. Each domain owns its models, logic, and boundaries. Domains communicate through well-defined contracts — never by reaching into another domain's internals.

- **Ubiquitous Language**: domain models and code reflect the language of the problem space (agents, conversations, tools, providers).
- **Bounded Contexts**: each domain has clear boundaries and single ownership of its concerns.
- **Aggregates**: consistency boundaries are enforced through aggregate roots.
- **Domain Events**: side effects across domains are communicated through events, not direct calls.

### CQRS (Command Query Responsibility Segregation)

Commands and queries are separated:

- **Commands** mutate state and do not return data. They go through domain logic, validation, and specification evaluation.
- **Queries** return data and have no side effects. They bypass domain logic and use optimized read models where beneficial.

### Specification Pattern

Business rules and validation logic are encapsulated in composable Specification objects. Specifications can be combined (and, or, not) and are evaluated against domain objects before mutations are applied.

### Anti-Corruption Layers (ACLs)

Any external system or platform-specific concern is isolated behind an Anti-Corruption Layer. The domain never depends directly on external SDKs, platform APIs, or infrastructure. ACLs translate between the domain's ubiquitous language and the external system's concepts. An ACL exists because its seam earns its keep — each table row states why the seam exists.

The doctrine this refines: ACLs share no **domain** code; provider wire plumbing may live in a shared infrastructure project.

## Technology Stack & Constraints

- **Runtime**: .NET 10
- **Language**: C#
- **Platform**: Windows only — all path handling, process execution, and scripting assume Windows.
- **Exec / Scripting**: Roslyn C# scripting via the Exec ACL (`IExecEngine`) — no PowerShell anywhere in the solution. External processes (e.g., `git`) are spawned directly with native .NET `Process` APIs.
- **AI Providers**: OpenRouter — the domain model speaks in provider-neutral concepts, and each provider's ACL implements them. Sessions are wired exclusively for one provider; switching providers is a different experience by design.
- **Interface**: Desktop (Avalonia)

### Packaging & Wiring

- Each domain and ACL is its own project (package) for composability.
- Packages are designed to be swapped or extended — replacing an ACL implementation must never require touching domain code.
- Dependency injection wires implementations at the composition root; domains depend only on interfaces and contain zero DI container references.
- `eThangAgent.ComputerUse.Host` is the supervised broker executable: it serves the computer-use NDJSON pipe, walks UIA trees, captures frames, and injects input — the killable native side of the ComputerUse ACL.

## Domains

Each concern is owned by exactly one bounded context. When adding code, first ask which domain owns the concern — if the answer is "more than one" or "none", the boundaries need attention before code is written.

- **Agent Domain**: the core agent loop, conversation orchestration, tool dispatch, execution flow, and sub-agent spawning/runtime.
 A per-session watchdog (`AgentWatchdog`, application layer; pure policy in the Agent Domain) re-homed on supervisor events: each tick (default 60 s) it iterates the `ChildSupervisorRegistry` — one `ChildSupervisor` per running child, fed by the supervisor event stream (`ChildEventStream`), no sweep-based discovery and no wall-clock child timeout (ChildTimeout was deleted; wall-clock is never a cancellation source). Cancellation sources are exactly three: explicit interrupt, a watchdog terminal decision, and the budget hard ceiling. Supervisor facts are fed by a `SupervisorFeed` subscriber (progress events drive idle clocks/phases; settles retire supervisors) — subscribed by `AgentWatchdog` itself. The feed's per-event-kind contract is decided once and pinned (`SupervisorFeedContractTests`): progress events beat and phase, started events beat (the runtime mints a fresh supervisor per (re)start), while budget alerts, preemptions, mail deliveries, and mailbox drains never beat; idle alerts never feed (published under the supervisor's non-reentrant lock — an echo would self-deadlock and clear the alert being raised). Remote-mode children get idle detection HOST-side: the ChildHost attaches a `HostChildWatchdog` per child run (same policy, enacted through the host's own runtime), so a hung-but-under-budget remote child is retried/failed locally; the app never guesses from absent beats. The host watchdog's knobs are operator configuration, not constants (W1.2): strict-bound watchdog preference keys (`subagent_watchdog_tick_interval`, `subagent_watchdog_idle_threshold`, `subagent_watchdog_max_wrap_up_attempts` — constant-format durations, invalid text is a startup error, never clamped) ride `AgentSettings.Watchdog` into the host's settings JSON and govern `HostChildWatchdog` through `SessionHost.EffectiveWatchdogOptions`; absent keys mean `WatchdogOptions.Default` everywhere. A first idle breach (default 15 min, from supervisor facts — heartbeats are liveness hints for other containers, not the decision input) cancels the run and restarts the SAME child id on a wrap-up nudge with its partial transcript preserved and re-hydrated; a second breach marks the child Failed(Hung); a `HardCeilingReached` supervisor flag enacts an interrupt audited as budget exhaustion. Every decision is an append-only row in the `watchdog_events` table (`IWatchdogEventStore`, Storage ACL), which also carries observe-only app-RSS records and dispatch-time grant-violation audit rows. App-RSS ownership is process-lifetime: a `ProcessRssMonitor` (application layer; `IProcessMetrics` + the process-level event store, started by the Desktop beside its `WatchdogLoop`) samples the working set with no tabs required, rate-limits `RssBreached` rows, and appends one `RssSustained` row per sustained-breach episode — the hook a future force-recycle policy will key off. The per-session watchdog samples nothing; the remote ChildHost owns none either (its `WatchdogServices` carries no metrics). The Desktop hosts one `WatchdogLoop` per process, attaching/detaching per open tab. Children are spawned through `agent.spawn` (priority queue holds records — start is non-blocking per FR-L1), awaited with `agent.wait` (one await over `WhenSettledAsync`, the documented idiom — status is a projection for humans, not a poll target), resumed for fix rounds with `agent.resume` (re-enters a SETTLED child — completed or failed — on the same id with a fix-round message; transcript, workspace anchor, and grants carry over; remote children report `Error [ResumeUnsupported]` until the wire transport op lands; in-process), and steered mid-run with `agent.send`/`parent.send`: push-delivery into bounded per-agent mailboxes (`BoundedAgentMailbox`, between-turn durability through `IMailboxStore`), urgency levels with policy-gated audited preemption, `notify-subtree`/`notify-ancestors` broadcast with per-target receipts (`hop=<n> to=<id> delivered|NotRunning|MailboxFull` lines plus a `reached=<count> delivered=<count>` summary; walking persisted `ParentId` links down through `IAgentQueries.ListChildrenAsync` and up through `GetStatus`), and `InterruptSubtree` deepest-first) plus `agent.fanout` for fan-out/fan-in spawn graphs (the `children` argument is parsed strictly — empty arrays, non-string model/label values, and malformed specs are rejected at the door as `InvalidActionInput`; a failed start such as `DepthExceeded` propagates its own code verbatim, honoring the action's advertised fail-fast join). Mailbox lifecycle publishes on the child event stream — `MessageDeliveredEvent` on deliver, `MailboxDrainedEvent` when the owning loop drains at a safe point (classified no-beat in the supervisor feed, like every mailbox-lifecycle event) — and the Desktop session tab renders the child subtree's unread-steering badge from that subscription (push-only; headless hosts attach nothing). Action names admit interior hyphens since W4 (the broadcast vocabulary; action names are strings end-to-end — dispatch by switch, grants/receipts as JSON keys — and no C# identifier is generated from them). Spawn-time capability grants (`tool.allow`/`tool.deny` on the persisted `SpawnContract`) are enforced at DISPATCH: the spawn command resolves the child's effective set from the parent's persisted resolution (or the session's child tool surface) and persists it, the child's loop registry is a `FilteredToolRegistry` and its exec capability registry a `FilteredCapabilityRegistry`; denied dispatches return the verbatim `Error [GrantViolation]: tool '<name>' is not granted to this agent.` and append a `GrantViolation` audit row. Grants are namespace-aware (issue #108): an entry ending in `.*` is a namespace pattern (`mcp.github.*`) whose dispatch root (`mcp`) rides the effective set so the dispatch tool resolves; a bare root allow inherits the parent's pattern reach (a child granted bare `mcp` reaches exactly the parent's reach); widening is measured over namespace reach (a pattern must nest within a parent pattern or a patternless root; an unexpressible deny subtraction is a spawn-validation error) — and the resolved entries ride the child's run as the ambient `McpGrantScope` (AsyncLocal, the anchor-scope pattern): the `mcp` tool re-checks the RESOLVED id (`mcp.<server>.<tool>`) at dispatch and filters the listing to reachable servers. Mid-run revocation is out of scope (ledgered ruling). Child reports can carry a JSON `ResultSchema` (one repair round, then `Failed(InvalidResult)`); `SpawnGraphHandler` fans out/fans in named graphs with per-member receipts; `AgentLinkRegistry` holds consent-required, revocable named links, PERSISTENT per workspace (W2, superseding the R2.3 in-memory v1 ruling): the registry is store-backed (`ILinkStore`, SQLite `agent_links` table via migration V12) — hydrated at construction, written through at consent (a consent failure never touches the store; a store failure rolls back and surfaces), deleted at revocation (revocation is permanent; hydration failure is a named infrastructure error). `agent.route` therefore works in any later session over the same workspace; a link whose target agent row is gone still resolves and fails `NotRunning` honestly.
Cross-container delivery (W3) makes links dialable: `IAgentMailboxLocator` (Agent Domain) is
consulted by `agent.route` when (and only when) the local runtime fails `NotRunning`; the
composition wires a process-wide `ProcessMailboxLocator` that every opened session
contributes its live mailboxes to (in-process children via the container registry, remote
children via a `RemoteMailboxProxy` that forwards over the wire to the host's mailbox
enqueue, owned ids only). Same-process scope by contract — a second app instance stays
unreachable and reports `NotRunning`. Receipts, error codes, and the R2.4 resolve-reveals-
address-only rule are unchanged; a cross-container delivery publishes
`MessageDeliveredEvent(direction "cross-container")` on the TARGET container's stream. Link creation's door is the Desktop's per-tab **Links** dialog (🔗 rail entry): the user names a link and consents to a target agent, the dialog registers it consented on the selected tab's registry — the SAME object `agent.route` resolves through — and can revoke it; no other production caller of `Link` exists. `agent.route` resolves a name and delivers to the linked address (unresolved names fail `NotLinked`); resolve reveals ONLY the address tuple (`Name`, `Container`, `AgentAddress`) — never consent state or metadata (R2.4 trust test). `agent.escalate` walks N ancestor hops with a per-hop receipt line (`hop=<n> to=<id> delivered|NotRunning|MailboxFull`), stopping at the root with `reached=root` (R2.2, FR-C7 per-hop visibility). Out-of-process children ride `eThangAgent.ChildHost` + `eThangAgent.Transport.ACL` (opt-in; see the Transport ACL row); the design record for the whole subsystem lives at state key `specs/2026-07-19-subagent-system`. Sessions ARE the domain's root agents: every turn persists its full message slice (user, assistant tool-call messages, tool results, nudges) losslessly through `IAgentStore`, CHILD runs persist INCREMENTALLY — the Agent subscribes to conversation mutations (`Conversation.Subscribe`) and flows every message through `IChildTranscriptStore`/`ChildTranscriptStore` to the store at the safe point it is added, always with `CancellationToken.None`, so an interrupt or crash leaves the run's transcript persisted up to the last safe point (the 2026-10-04 incident erased a 31-minute child because terminal persistence ran under the cancelled run token); terminal persistence (flush + terminal row) also runs under `CancellationToken.None`, and a persistence fault throws `TranscriptPersistException`, which the runtime catch-all reports honestly as `failed to persist child transcript` — never the misleading `A task was canceled.` —, and the host shell's **Sessions** menu (Desktop left-menu entry) lists persisted root sessions via the session catalog (`SessionCatalogQueryHandler`), newest first, greying out ones already open in a tab. The catalog lists only RESUMABLE rows: a depth-0 record whose bound provider this build no longer knows (e.g. a session persisted under the retired z.ai provider) is omitted — resume would fail `UnknownProvider`, so the dead entry is never offered. The gate is the optional `isResumableProvider` predicate wired to `Providers.IsKnown` at the composition root, keeping provider identity out of the domain, and `Providers.DisplayName` renders an unknown id as its raw text instead of throwing, so a display surface never crashes on historical data. Confirming a row resumes that session by id — the factory rebuilds the container on the session's ORIGINAL provider and workspace and hydrates the conversation from the persisted transcript, so the conversation continues where it stopped. Opening a workspace always mints a NEW session — resume is manual via the menu, never automatic for a directory. `AgentRecord`'s workspace/provider columns are discovery metadata only: they never scope conversation content, and unrelated sessions in one workspace share nothing conversational (only the deliberately workspace-scoped durable stores — state keys, curated memories, failover exclusions, picker preferences, consented links — carry across a workspace's sessions). The agent loop carries two optional collaborators wired via `AgentOptions`: `IContextMonitor` (per-provider-call usage accounting), `IContextCompactor` (auto-compaction at the 80% utilization threshold — the oldest exchange groups are replaced by an LLM handoff summary; a compacted root turn persists by transcript replacement, not the append slice; the trigger distrusts a provider-reported input-token count far beyond the conversation's own character estimate (server-side tool calls ride the provider's accounting without entering the history — firing on them fails spuriously with CompactionImpossible). The same compactor also recovers in-loop from a context-window overflow: the OpenRouter ACL maps an HTTP 400 whose body names the context-length fault to the distinct `ContextWindowExceeded` error code (other 400s stay `ProviderError`), and the loop answers that code with one forced compaction and one retry — a second overflow, a compaction failure, or no wired compactor fails the turn (`CompactionUnavailable` when nothing is wired), never a silent loop. The model can also shrink its own context at a milestone: the `context_edit` tool (Tool Domain, over the `IConversationContextService` port adapted from the Conversation Domain's `ConversationContextService`) renders the indexed message list and removes/shortens selections through `Conversation.Compact`'s protocol invariants; a successful shrink returns the verbatim `[context: shrank ...]` sentinel, which the loop reads to rest auto-compaction for the turn and (root and child alike) switch persistence to whole-transcript replacement (`TurnCallbacks.OnContextShrunk` carries the signal to hosts). Absent collaborators mean byte-identical legacy behavior.
- **Conversation Domain**: message history, message shapes (including tool calls and tool results), and conversation state. A `Conversation` can be seeded from a persisted transcript (resume hydration). `Conversation.Compact` replaces the whole message list behind aggregate invariants (non-empty, tool-call/result pairs intact, no dangling ids) — compaction summaries are System-role messages flagged `IsSummary`, serialized as ordinary system messages by both ACLs.
- **Tool Domain**: tool contracts, input validation, tool execution, tool result processing, and built-in tools — including the agent's read-only self-database inspection (`db_schema` / `db_query` over the `ISelfDatabaseAccess` seam, enforced by the Storage ACL's read-only connection), arbitrary workspace SQLite files (`sqlite_query` over the `ISqliteFileAccess` seam), and the `command_output` read-back for `!` chat commands (`IShellCommandAccess` / `ICommandRunStore` seams; runs persist per workspace in `command_runs`, migration V14), file-name search (`find_files` over the `IFileSearchAccess` seam, Win32-glob name matching with standard build/VCS exclusions and a result cap — one call replaces the recurring list-everything-then-enumerate probe pattern) — plus the `worktree` tool (list/create/remove of git worktrees behind the `IGitWorktreeAccess` seam, native-git adapter in the FileSystem ACL; created under `.worktrees/` on a `worktree/<name>` branch off HEAD, dirty worktrees refuse removal unless forced; the main worktree is never removable) and the spawn-time workspace anchor (`SpawnRequest`/`SpawnContract` carry an optional `WorkspaceRoot`, validated in `StartSpawnHandler` by `WorkspaceAnchorSpecification` — `AnchorMissing` unless it is a non-empty absolute path to an existing directory, `AnchorInvalid` when it resolves outside the parent's effective root — and enforced via `AnchoredToolRegistry` + `IWorkspaceAnchorScope` in `SubAgentSpawner` and the composition's exec delegate, so the child's exec scripts resolve at the anchor, and registry re-rooting engages for workspace-scoped tools when they are present in the child registry; the exec-path capability surface is re-rooted the same way — `AgentToolsProvider.RootedAt(anchor)` feeds the composition's memoized anchored registry, so the child's path-rooted tools resolve at the anchor and refuse paths outside it, and an anchored parent spawns anchored children by default (a workspaceRoot-less spawn inherits the parent's anchor); the `computer` tool is an action-switch tool over the `IComputerAccess` seam with strict input validation and the standard `Error [CODE]` error contract, and multimodal tool results flow `ToolResult.Images` -> `Message.Parts` -> the provider wire with the model's `AcceptsImageInput` vision capability gating screenshot attachment) — the `Mcp` persistence seam (`IMcpServerStore` + `McpServerConfig` / `McpOAuthTokens` / `McpTransport` / `McpApprovalState` / `McpGateMode` / `McpDecision` under `eThangAgent.ToolDomain.Mcp`, implemented by the Storage ACL's `SqliteMcpServerStore` over the V15/V16 tables) and the `mcp` dispatch tool (issue #104: the model's single door to configured MCP servers — one tool on the loop registry so the definition budget stays flat no matter how many servers are configured, B1; `list` reports configured servers with connection state and never connects, `call` connects lazily on first dispatch and caches the tool list per workspace, a failed connect is a structured `McpConnectFailed` error plus a status entry with the next call retrying, unknown server/tool fail `McpServerNotFound`/`McpToolNotFound` naming what IS configured, and pending/revoked servers refuse `McpServerNotApproved` — over the `IMcpServerAccess`/`IMcpClientSessionPool`/`IMcpServerAccessProvider` seams, implemented by the MCP ACL over the official SDK) — and the `skill_invoke` user-invocation tool over the Tool Domain's `ISkillInvocationPort` + `IConversationSink` seams (Tool Domain cannot reference Conversation Domain — the reference runs the other way — so the composition root adapts the session `Conversation` to the sink; the shared core is the Agent Application's `SkillInvocationService`, surfaced on `AgentSession.SkillInvocation` for the Desktop).
- **Model Domain**: model capabilities, provider contracts, model configuration, and model+provider selection (`IModelSelector`, `IModelCatalog`, `IntelligentModelSelector`, `RootAgentResolver`, `ProviderFailoverResolver`, `SessionModelPreferences`). Context accounting lives here too: both ACLs report provider-scored `TokenUsage` on every response, `ModelConfig` carries a nullable `ContextWindow` — null means not yet catalog-resolved (bootstrap configs); every serving model's window resolves from the provider catalog through `IContextWindowSource` (no curated constants exist; OpenRouter's `openrouter/auto` is a fetched catalog row at its API-reported size), and a catalog miss fails the turn/spawn loudly (never a fabricated window), and `ContextAccountant` (`IContextMonitor`) keeps utilization against that window — provider usage reports are the only decision input; character-based numbers are estimates for UI breakdowns only. Selection runs automatic selection — a two-stage LLM pipeline picking on cost (after discount), latency, throughput, and capability scores (intelligence, coding, agentic), deferred to the first user prompt (not startup) and re-run every 10 user messages. The user overrides selection through the host's model picker (the Desktop Model Settings window's **Model** section: an **Auto** row plus a searchable catalog list; the standalone model/effort rail entries are gone — grand-plan item 117); the choice lands in `SessionModelPreferences` and outranks automatic selection from the next turn, root and children alike, and the Desktop persists it per workspace + provider so reopening a directory restores it. There is no configured model pin — model choice is runtime-only. Failover re-selection excludes failed model+provider pairs via a SQLite-backed exclusion store with TTL. `SessionModelPreferences` carries runtime-adjustable knobs — reasoning effort and model, both via the Model Settings window, plus TWELVE provider-neutral sampling knobs (top-p, top-k, frequency/presence/repetition penalties, min-p, top-a, seed, verbosity, parallel-tool-calls, and the temperature and max-tokens caps) set through the Model Settings window. Every knob is a nullable runtime preference: a null knob is OMITTED from the request body so the provider default applies — true for the ten nullable sampling knobs, while temperature and max-tokens are non-nullable on `ModelConfig` and always travel (a null preference there means the app-resolved default, not an omitted key). The `ModelPreferencesOverlay` overlay carries them onto every resolved config (root and children alike; the failover resolver currently builds configs without the overlay — latent only, no production consumers today); OpenRouter-only request settings (provider routing, the ten server tools available on the responses API (openrouter:subagent was removed as an option — its server-side agent loop cannot complete inside the request timeout, and the harness owns subagents natively), plugins, loop budgets) are typed in the OpenRouter ACL (`OpenRouterRequestSettings`) and travel as OPAQUE JSON in `ProviderSettings` — domain code never interprets them —. The effort choice — model default or one of seven levels — maps to OpenRouter's unified `reasoning.effort` and is persisted + restored per workspace + provider.
- **Capability Domain**: the registry that merges providers and exposes tools and capabilities to the model.
- **Memory Domain**: recall and search over persisted sessions (lexical and bounded-regex query planning), plus the curated-memory learning loop (categorized, tagged, full-text searchable, versioned).
- **Skill Domain**: the methodology-skill subsystem — three skill sources under one contract. Embedded built-in skills ship verbatim (`EmbeddedSkillCatalog` over SKILL.md resources in the Skill Domain assembly, including the using-skills session contract and the ethang-tools-mapping tool-binding skill); file skills load from user-configured directories in agentskills.io format (each immediate subdirectory holding a SKILL.md, or a SKILL.md at the directory root, is one skill — everything else in the folder is ignored); learned skills are agent-created, with version history and usage tracking. The `CompositeSkillCatalog` merges built-ins and file skills with precedence built-in > global-directory > workspace-directory — a file skill never shadows a built-in, and later same-name entries are shadowed with a `[collision]` diagnostic — while learned resolution falls through to the store only after a catalog miss. Frontmatter parsing (`SkillMarkdown`) demands `name` and a non-empty `description`; the honored agentskills.io keys are `metadata.version` (integer) and `disable-model-invocation` (a manual skill); known-but-unapplied keys (`allowed-tools`, `license`, `compatibility`) and unknown keys load with per-file warnings — warnings never fail a load, and one bad file degrades to a diagnostic, never a whole-load failure. Manual skills never appear in the always-on listing, carry a `[manual]` marker in `skill_list`, and load by name. Skill directories are host configuration: the `skill_directories:global` / `skill_directories:ws:{root}` preference keys (the same `{path, enabled}` JSON shape as the session-file lists), edited in the Desktop's Open Workspace dialog (moved out of the Settings window); nothing configured means no file skills. Every session (root, children, and remote — the ChildHost resolves the same directories from the settings it serializes via `AgentComposition.ResolveSkillDirectoriesFromSettings`) carries the `SkillsListingPromptProvider`'s budgeted listing: 8,000 characters total, descriptions truncated at 60 characters, grouped Built-in / Global directory skills / Workspace directory skills / Learned, `[collision]`/`[warning]` lines rendered, and a truncation marker whenever any description or entry was dropped — never silent. The session bootstrap (`SkillsBootstrapPromptProvider`) injects the using-skills contract verbatim — prefer a matching skill over improvising, announce it, load its body with `skill_view`, the user's instructions outrank skills — with no emphasis wrapper; the development-methodology skills are description-triggered from the listing, not session defaults. The tools: `skill_list` (builtin/file/learned source labels, the `[manual]` marker, catalog diagnostics), `skill_view` (the origin directory in the annotation for file skills; usage rows recorded for learned views only), `skill_manage` (refuses to create a name held by a built-in or file skill — `NameCollision` — and reports `BuiltInImmutable`/`SkillNotFound` on update or delete of either); the skill registry tools (`skill_search`, `skill_registry` install/update/uninstall with a deterministic BLOCK/advisory content scan and the `skill_registry:default_target` preference) install community skills into configured directories, surfacing same-session through hot reload. Deterministic user invocation (spec #28, superseding skill-routing spec #19 decision 6's gated user-invocation channel) runs through ONE application core: `SkillInvocationService` resolves a name case-insensitively over the full visible+manual catalog (0 hits -> `SkillNotFound`, >1 -> `AmbiguousSkill` listing the matches) and renders the verbatim `[skill invoked: <name>]` System line — description truncated at the 60-character budget, body inlined, a >4,000-character body falls back to a `skill_view` pointer (`SkipReason=oversize`), arguments ride a final `arguments:` line, and NO `skill_usage` row is written (view-hygiene rule). The channels: the `skill_invoke` tool (returns the one-line confirmation, never the body) and the Desktop's `/` slash input — a raw-first-character `/` (no trim) opens the `SkillAutocompleteViewModel` popup (manual skills first, case-insensitive substring filter over the name token, wrap-around navigation, Tab/Enter accept autofills `/<full name> `); at submit, a found name injects the System line then forwards the full input as the ordinary user message, an unknown name stays a plain message, and an ambiguous name sends nothing and surfaces a transcript notice listing the matches. A headless activation eval (`tools/SkillActivationEval` — `ETHANG_EVAL_KEY`, `ETHANG_EVAL_PROMPT_BUDGET_SECONDS`, `ETHANG_EVAL_LOCAL_BASE_URL`; deliberately not part of the solution) drives real sessions over `prompts.json` to measure skill activation, with before/after results captured as plan records.
- **State Domain**: durable, workspace-scoped key-value state, evidence-carrying transitions, and state events.
- **Plan Domain**: durable plan records — ids tied to owning sessions, ordered steps with optional todo references — persisted through the Storage ACL (`plans`/`plan_steps`, migration V13) and exposed through the `plan` capability provider; the SDD workflow's design specs and implementation plans are plan records.

Configuration concerns live with their consumers until a real Configuration context earns its own boundary.

## Project Structure

The solution follows a layered DDD structure. Each bounded context has its own project with:

- `Domain` — aggregates, entities, value objects, domain events, specifications, repository interfaces
- `Application` — commands, queries, handlers, application services
- `Infrastructure` — repository implementations, ACL implementations, external service adapters
- `Contracts` — public interfaces, DTOs, and contracts shared across boundaries (kept minimal)

Shared kernel (cross-cutting concerns shared across domains):

- `SharedKernel` — base types, common value objects, guard clauses, result types

ACLs live in an `ACL` project each, implementing domain-owned interfaces.

### Naming Conventions

- Domain namespaces omit the dot: `eThangAgent.ToolDomain`, `eThangAgent.ConversationDomain`.
- ACL namespaces keep it: `eThangAgent.OpenRouter.ACL`, `eThangAgent.FileSystem.ACL`.

## Development Conventions

- **No shell intermediary**: repo automation is plain `dotnet` CLI invocations; do not commit `.ps1`/`.sh`/`.cmd`/`.bat` scripts. If a task needs scripting, prefer C# (the same language as the codebase).

- **Build**: `dotnet build`.
- **Formatting & analyzer severity**: enforced mechanically — `.editorconfig`, `Directory.Build.props`, and the CI lint job are the source of truth; this document deliberately does not restate their rules. Apply with `dotnet format whitespace eThangAgent.slnx` before committing (apply analyzer fixes only per rule, never in bulk — `dotnet format` without a subcommand also applies semantic analyzer fixes and can rewrite signatures), then verify with the exact CI lint gate before pushing: `dotnet format eThangAgent.slnx --verify-no-changes --severity warn`. That verify command is a strict superset of the whitespace subcommand — it also runs style and third-party analyzers (the JSON001–005 family, e.g. `Probable JSON string detected`), which never surface on `dotnet build` even with `EnforceCodeStyleInBuild` + `TreatWarningsAsErrors`, because the family executes only in the format/IDE host and not the batch compiler; the verify run is their only automated net. (The signature-rewrite hazard is apply-direction only — `--verify-no-changes` writes nothing.) Sonar rules (SXXXX) are enforced at build time via `SonarAnalyzer.CSharp` (referenced in `Directory.Build.props`), mirroring the SonarQube Cloud profile: a finding must surface on `dotnet build`, not only after push. xUnit rules (xUXXX) are enforced at build time via `xunit.analyzers` (pinned in `tests/Directory.Build.props`; xunit.v3 3.2.x already pulls ≥ 1.27.0 transitively, so the pin exists to take 2.0.0's rule set ahead of the xunit.v3 4.x bump, which requires ≥ 2.0.0 and therefore conflicts with nothing). Named deviations live in `.editorconfig` (S1135, S125 off — their heuristics collide with this repo's prose) or targeted `#pragma warning` pairs at by-design sites (deliberate empty base records, provider base-URL constants, best-effort cleanup catches). Two carve-outs are named decisions, not leniency: CA1707 (xUnit `Method_Scenario_Expected` names) is suppressed in test projects only; CA2007 (`ConfigureAwait`) is suppressed in `eThangAgent.Desktop` only, because the UI SynchronizationContext is load-bearing — view-model continuations must resume on the UI thread. In test projects, awaits of same-assembly tasks use `ConfigureAwait(true)` in xUnit test methods and `ConfigureAwait(false)` in fake/helper classes (xUnit1030 forbids `false` in test methods).
- **Testing**: xUnit. Three layers: unit, integration, and E2E tests. Solution-level `dotnet test eThangAgent.slnx` runs every test project concurrently (Microsoft.Testing.Platform: one testhost per project, up to `Environment.ProcessorCount` modules at once); on a loaded machine the timing-sensitive integration tests (named pipes, git worktrees, Roslyn shell kills) can contend — pass `--max-parallel-test-modules <n>` (e.g. 4) to bound the concurrency. There is NO desktop-driving computer-use test suite: the owned-window integration tests were removed deliberately (they popped real windows and raced the user's own desktop use); computer-use coverage is stub-host supervision tests, wire/contract tests, and the fake-access E2E — nothing creates windows or injects input on the user's desktop. Aim for 100% coverage; minimum 80% required. Unit tests use fakes only — a domain test must never know PowerShell, HTTP, or OpenRouter exist. Integration tests exercise real ACL implementations against real files / sandbox endpoints. E2E tests drive the desktop app headless — real composition behind the view-model — against a local mock provider server. Test selection runs on the xunit.v3 / Microsoft.Testing.Platform runner, not VSTest: `dotnet test --filter` is rejected (exit 5, help dump) — use `--filter-class` (fully-qualified class name), `--filter-method`, `--filter-trait`, or `--filter-query`; the runner also rejects `--no-build` and `--nologo` (exit 5, help dump) — plain `dotnet test <project> --filter-class <FQN>` is the working form; exit 2 means failures, exit 8 means zero tests matched.
- **Session retrospective**: at the end of every session/task, evaluate how *the agent itself* handled the session — bugs in its behavior, gaps in its tool surface, missing skills or workflow support — and include that evaluation in the summary to the user rather than letting it evaporate. The retrospective evaluates and targets the harness itself — a general agent that can be used on any repository, in any language, for multiple users — never the host repo: suggestions must target the agent (new tools, capabilities, prompts, reliability), never one-off fixes baked into a specific repo. A pattern that recurs across sessions or repos is a signal to promote it into a first-class agent capability.
- **Deadlock vigilance in tests**: a test that can wait forever eventually will. Any test exercising an unbounded or externally-settled await (channels, gates, `TaskCompletionSource`) must have a reachable completion path under the code under test's *current* contract — before running the suite, trace what settles the await. When a contract changes from bounded to unbounded, update every test that relied on the old bound in the same change, asserting the new contract directly rather than scripting the old one. A hung test blocks the whole suite and the agent itself; after fixing the cause, kill the orphaned `testhost` process before rerunning.
- **Every change leaves the build green**: a task is not done if the solution does not build and all tests pass.
- **Green includes a clean tree**: a task is not done while `git status --porcelain` shows output. Intended changes are committed; unintended ones are reverted or surfaced. Uncommitted work is unfinished work.
- **Dependency injection**: all wiring at the composition root — the host-agnostic `eThangAgent.Composition` library (`AgentComposition`/`AgentSessionFactory`), consumed by the Desktop host. Domains depend only on interfaces and contain zero DI container references.
- **Immutability**: domain models prefer immutability — records, init-only properties, copy constructors.
- **Error handling**: result types, not exceptions, for expected domain failures. Exceptions are for infrastructure/programmer errors.
- **Tool design**: tools demand strictly correct input (see Guiding Philosophy). Tool errors are returned to the model as tool results — an error is feedback for self-correction, never a turn-ending crash. The loop's `ToolRepeatGuard` guards BOTH failure-loop shapes: identical-args nudges at the 2nd/5th identical failure, plus a cross-argument breaker that counts consecutive failures of one tool across ANY arguments, nudges at the 3rd and SUSPENDS the tool at the 13th (3+10) — the loop then refuses further calls with `Error [ToolSuspended]` without executing them (2026-10-04: ~200 varied failed exec calls never re-tripped the identical-args nudges). Model-facing output uses explicit format contracts (annotation lines, gutters) documented verbatim in the tool description, so the model never has to guess what it is looking at.
- **Performance**: hot paths (file reads, shell execution) go through in-process hosting where possible; avoid per-call process spawns. Streaming over loading: read only the requested range, then account for the whole. Aim for event-driven flow over polling loops, and keep steady-state memory small — don't hold what you're not using. Maintain high performance, low latency, low memory, and a modular event-driven architecture across every change.
- **Create tools as you work**: when something useful is missing, add a tool for it rather than working around the gap. Tools are the agent's first-class surface — a missing capability is a missing tool, not a one-off script. New tools follow the existing `ITool` / capability-provider contracts: strict input validation, `Result<T>` errors, and verbatim format contracts in the description.
- **Prefer tools over exec scripts**: the Roslyn `exec` engine is for one-off glue, not a substitute for first-class capabilities. When the model keeps writing the same or similar scripts across sessions — repeated file probing, shell-out patterns, query shapes — that is a signal to promote the pattern into a general tool with proper validation and format contracts. The model should spend its effort on decisions, not on re-deriving boilerplate C#.
