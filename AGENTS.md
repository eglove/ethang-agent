## What This Project Is

eThang Agent is an AI agent harness built with .NET, delivered through an Avalonia desktop application. The project follows strict Domain-Driven Design: layered bounded contexts, Specification patterns, and CQRS.

> **Read [`README.md`](README.md) first** — it carries the high-level overview and usage instructions. Whenever a change makes either stale, update the README in the same change.

## Overall Goal

eThang Agent exists to make model quality stop mattering.

The harness is not a developer tool. It is a stakeholder tool: anyone who can state what should be true can use it, and everyone who uses it becomes a stakeholder in the outcome. Implementation details — decomposition, tool selection, sequencing, verification, recovery — belong to the harness and the model, not to the person directing the work.

Two commitments follow:

1. **Any work is doable by any model.** Complex work is decomposed until none of it requires smartness. The least intelligent model can complete complex tasks because the harness supplies the structure: skills for matched procedures, the scientific method for non-trivial work, verification gates, and tool contracts that make the next step obvious.
2. **Judgment is the only scarce resource.** The one thing the harness cannot supply is judgment about what the constitution should say — what the work is, why it matters, and when it is done. That remains with the user.

In short: the user decides what should be true. The harness figures out how to make it true.

## Guiding Philosophy

These principles explain every convention below. When a rule seems arbitrary, it traces back to one of these.

- **Seams over commitments.** Every external dependency — AI provider, shell, file system, UI — sits behind an interface the domain owns. Nothing external is ever allowed to become load-bearing inside a domain. Any implementation behind a seam must be replaceable without touching domain code.
- **Strict correctness at the boundaries.** Inputs crossing into the domain are validated completely: required parameters are required, types are exact, unknown input is rejected, and nothing is silently coerced, defaulted, or clamped. Deliberate exceptions exist but are named, documented decisions, never defaults — each proves the rule: (1) a benign overshoot that is clamped with a visible warning; (2) a nested exec-script tool call that omits timeoutSeconds inherits the enclosing exec call’s budget (restating the budget per nested call cost real sessions repeated failures; explicit nested values still win and are still validated; the inherited budget is INJECTED only into actions whose contract declares timeoutSeconds, and STRIPPED from the rest — so every ITool-backed action must declare the parameter, guarded by a composition-level invariant test — and an exec run that completes with empty output while nested calls ran is annotated with a discarded-result hint; a program that references Directory.GetCurrentDirectory() carries a workspace-note annotation stating the launch directory and the workspace root, because the two differ and scripts that confuse them silently read the wrong directory); (3) a nested exec-script tool call refused with an argument-shape error — InvalidParameterValue or MissingParameter — by an action declaring `ValidatesArgumentsBeforeDispatch`, which returns as an in-band `Error [Code]:` result the script branches on instead of throwing and killing the whole program (issue #259: the remedy is the same call with the argument the error names corrected, so the call has a legitimate continue-path and the throw cost a mandatory round trip per occurrence; the same codes from an action that does not declare it — an error reported after the call did work — still throw, because a partially applied batch passing silently is the buried failure that rule exists to prevent).
- **Errors are information, not crashes.** Expected failures flow through `Result<T>` / error values and are delivered to whoever can act on them — including the model itself, which receives tool errors as tool results so it can self-correct. Exceptions are reserved for programmer error.
- **Reversibility by construction.** The architecture must not preclude alternative frontends, platforms, providers, storage engines, or orchestration topologies. When a choice would foreclose an option, choose the seam instead.
- **The codebase is not the standard.** Existing code records what was done, not what is right. Never treat a current pattern as best practice just because it is present — when work touches code and a better way exists, improve it in the same change. Improve what you touch; do not launch unrelated refactors.
- **Lean, event-driven operations.** Aim for high performance and a small memory footprint. Prefer event-driven designs — react to what happened instead of polling, stream instead of loading, and don't hold what you're not using.
- **Direction: a self-contained agent.** The long-range shape (per the grand plan's philosophy, not its plan details) is a persistent desktop application that manages its own world — conversations, sessions, state, configuration — in app-owned structured storage rather than scattered project-level files. Work written today must fit that destination: durable state flows through domain-owned stores, never ad-hoc files.
- **Mechanical solutions first.** Harness features should prefer mechanical solutions, or mechanical checks as a supplement to model actions, wherever possible. A model action should be the fallback, not the default — when a task can be done by a tool, a validation, a specification, or an automated gate, build that instead of asking the model to do it by hand.

## Architecture Principles

### Domain-Driven Design

The codebase is organized around business domains, not technical concerns. Each domain owns its models, logic, and boundaries. Domains communicate through well-defined contracts — never by reaching into another domain's internals.

- **Ubiquitous Language**: domain models and code reflect the language of the problem space (agents, conversations, tools, providers).
- **Bounded Contexts**: each domain has clear boundaries and single ownership of its concerns.
- **Aggregates**: consistency boundaries are enforced through aggregate roots.
- **Domain Events**: side effects across domains are communicated through events, not direct calls.

### CQRS (Command Query Responsibility Segregation)

Commands and queries are separated:

- **Commands** mutate state and do not return data. They go through domain logic, validation, and specification evaluation.
- **Queries** return data and have no side effects. They bypass domain logic and use optimized read models where beneficial.

### Specification Pattern

Business rules and validation logic are encapsulated in composable Specification objects. Specifications can be combined (and, or, not) and are evaluated against domain objects before mutations are applied.

### Anti-Corruption Layers (ACLs)

Any external system or platform-specific concern is isolated behind an Anti-Corruption Layer. The domain never depends directly on external SDKs, platform APIs, or infrastructure. ACLs translate between the domain's ubiquitous language and the external system's concepts. An ACL exists because its seam earns its keep — each table row states why the seam exists.

| Exec ACL (Roslyn) | Runs model-authored `exec` programs and evidence checks via Roslyn C# scripting (`CSharpScriptExecEngine`, `CSharpEvidenceRunner`). **Every completed run reports the workspace files it actually changed (issue #283)** — `[exec: modified N workspace files — <paths>]`, or `[exec: modified 0 workspace files — the program completed but changed nothing]`. The report is a FACT about effects, not advice and not the API used: `Tools.write`, `Tools.edit`, and a raw `File.WriteAllText` are reported identically. **CONTENT DECIDES, NOT METADATA** — the engine takes a content-true `WorkspaceSnapshot` before and after the run (`IWorkspaceSnapshotAccess` → `DirectWorkspaceSnapshotAccess`, which hashes every file under `WorkspaceSnapshotLimits.MaxHashedBytes` and falls back to (length, last-write) above it), because the defect the report exists for is a read-modify-write whose anchor did not match: the file is written back byte-identical, so its timestamp moves and its content does not, and a metadata comparison would report a change that never happened — a confident lie, worse than silence. **A FILE WATCHER CANNOT DO THIS JOB** (measured 2026-10-25 and recorded at state key `specs/283-watcher-vs-snapshot-probe`): a `FileSystemWatcher` fires on a no-op rewrite (2 `Changed` events, bytes identical), sees every write under excluded directories (15,013 events for a build-shaped burst, `bin=10000`), delivers asynchronously after the script returns, and drops events silently on buffer overflow — it reports WRITES, not CHANGES, so it can never satisfy 'modified 0'. A watcher is invalidation (idempotent, self-healing); a snapshot is attribution (a claim needing content comparison). The walk is bounded by `WorkspaceSnapshotLimits.MaxFiles` and prunes `bin`/`obj`/`node_modules`/`.git`/etc. as whole path SEGMENTS (so `obj` never hides `objects`); a truncated walk says so in the line and never claims completeness. A host with no snapshot seam produces byte-identical output to before. The domain knows nothing about compilation or scripting internals; the engine resolves each script's `Workspace` through a host-supplied resolver (the session's workspace identity), never a process-global cwd. A RELATIVE path in a raw `File.*`/`Directory.*` call inside a script is the same trap and is fixed the same way: the engine exposes `ResolvePath(path)` (and `PathResolver`), which resolves at the WORKSPACE and refuses a path that escapes it — the 2026-10-22 leak (a `personal-vault` session wrote `p1.txt` and `doc161.pdf` into the `ethang-agent` repo because the raw call resolved against the app's launch directory) is closed, and the exec guide's old advice to "use relative paths" is CORRECTED (it was the cause). The ChildHost's process working directory is its own SCRATCH folder under the temp root, never the workspace: a child whose working directory sits inside the workspace PINS that directory and deletes over it fail while it lives (the git `-C` hazard). The 2026-10-19 leak (15 GB working set, 9.3M handles over ~200 exec calls) was the SERIALIZER pinning the collectible context: a script that hands a type it DECLARED (an anonymous type; also `Output(...)` arguments and tool argument objects) to `System.Text.Json` made the serializer cache that `Type` STRONGLY in its static `JsonSerializerOptions.Default` singleton (`_lastTypeInfo` / `CachingContext`); a cached `Type` holds its `m_keepalive` -> `LoaderAllocator` -> the collectible submission assembly, so the ALC could NEVER be reclaimed - one leaked context, assembly, metadata set and handle/thread bookkeeping set per call, uncollectable even under an aggressive compacting gen2 collect. The fix is `ScriptValueJson`: a PROJECTION that renders the value into default-context types (`Dictionary<string,object>`, `List<object>`, boxed primitives) and hands THAT to the serializer, so the serializer caches only types that live in the default context forever. Three independent vectors, each with its own regression test: the return value, an `Output(...)` argument, and a tool's argument object. The JSON output is byte-identical to before. **`exec` CANNOT DRIVE THE NATIVE DESKTOP SURFACE (issue #282).** A script could declare `[DllImport("user32.dll")] static extern bool SetCursorPos(int, int);` and drive the user's real desktop — move their window, steal focus with `SetForegroundWindow`, dispatch hardware-level clicks with `mouse_event` — entirely around the ComputerUse ACL, which exists to supply four guarantees the raw surface has none of: killable containment (a Job Object around a broker process, where an exec script runs INSIDE the app process and cannot be killed), an audit trail, a foreground/focus policy, and a grant surface. The sharpest consequence: `computer_use_enabled` defaults to OFF and gates only tool REGISTRATION, so a user who deliberately left computer use disabled still had their cursor moved. `NativeInteropPolicy` closes it at the seam the ACL already owns — the same `Compilation` validation already builds, so it costs no extra compile and loads no assembly (the leak contract above stays intact). It refuses the three declaration shapes that reach native code (`DllImport`, `LibraryImport`, an `extern` method) AND the two attribute-free escape hatches that reach the same place (`NativeLibrary.Load`/`GetExport`/`TryLoad`/`TryGetExport` and `Marshal.GetDelegateForFunctionPointer`) — blocking only the attributes would leave a one-line rewrite as the bypass, and a gate a rewrite defeats is not a gate. The refusal is a named `Error [NativeInteropBlocked]` that NAMES the `computer` tool, because the redirect is the point: a model told only 'no' retries with a different spelling. It is enforced on BOTH compile paths (`CSharpScriptExecEngine.ValidateAsync` and the run path, so a caller that skips validation cannot run a native call; and `CSharpEvidenceRunner`, a second independent compile path over the same Roslyn surface, or storing a native call as a `goal/check` command would bypass it). **THE ALLOWLIST IS EMPTY, BY NAMED DECISION**: the issue offered a narrow carve-out for 'genuinely harmless externs', and it is deliberately not taken — an allowlist keyed on a library name cannot distinguish `GetTickCount64` from `SetForegroundWindow` (same declaration shape, same DLL), so a carve-out would have to enumerate entry points and every entry point added is a permanent hole somebody widens later. Process-level needs are already covered by `Shell`; desktop needs by the `computer` tool. `NativeInteropPolicy.AllowedEntryPoints` is exposed rather than inlined so a test pins its emptiness: populating it is a product decision that must update that test and this row in the same change, never a quiet widening. The gate is UNCONDITIONAL — it does not read `settings.ComputerUse`, because an enabled computer tool is not a licence to bypass the containment, audit trail, and focus policy the broker exists to supply. | The execution engine is an implementation detail of the platform, not of the domain. |
| File System ACL | All file I/O goes through a domain interface (`IFileSystemAccess`). The domain never touches `System.IO` directly. Anchor-mode edit misses quote the file's nearest matching region in the failure (`Nearest match at line N` + context lines in the read tool's gutter format, Levenshtein similarity over trimmed lines with a 0.6 emission threshold) and then emit that region's own text as a ready-to-use `old`, so the retry is a paste and never a re-read (issue #252). The similarity figure is computed over TRIMMED lines, so a whitespace-only difference scores 100% and would read as a contradiction next to a failure — that case states the mismatch kind instead of the figure, and the detector compares both spans with all whitespace removed (issue #259). `ReadLinesAsync` stats the file FIRST and returns a `FileVersion` (Length, LastWriteTimeUtc) with the content — the read-back freshness guard's content-true token (issue #117): a write racing between the stat and the read makes the token older than the content (the next read over-delivers, never wrongly elides). Written text is LINE-ENDING NORMALIZED mechanically (issue #251): `WriteFileAsync`, `WriteFileLinesAsync`, `ReplaceInFileAsync`, and `ReplaceLineRangeAsync` rewrite the incoming text into the target file's own DOMINANT convention (an existing file is never restyled), or for a new file into the PROJECT convention resolved by `ILineEndingPolicy` (`EditorConfigLineEndingPolicy`: nearest `.editorconfig` `end_of_line` with section-glob matching and `unset` withdrawal, then nearest `.gitattributes` `eol=`, then the workspace's existing majority over an excluded enumeration, then LF), and every outcome reports it (`FileWriteOutcome`/`ReplaceOutcome.NormalizedTo`) so the tool annotation states it (`..., LF|CRLF line endings`) and the model never hand-rolls EOL handling in a script — the failure this replaced. Multi-hunk edits (issue #252) run through the same seam: `ReplaceHunksAsync` matches EVERY hunk against the file AS IT STANDS (never against another hunk's output), refuses touching matches as `HunksOverlap` rather than applying them in some order, and writes once — so a failure leaves the file byte-identical and a half-applied patch cannot exist; each hunk's replacement is normalized to the file's dominant convention exactly as anchor mode's is. Anchor-splice matching is unchanged: it still runs on normalized views with the offset map preserving untouched bytes. The skill registry's git-clone/prompt/remove adapter (`GitSkillRegistryAccess`) also lives here, over the native-git adapter pattern. Git children spawn WITHOUT a `WorkingDirectory` — the `-C <repo>` flag anchors them — because a child whose working directory sits inside the workspace pins that directory (deletes over it fail while the child lives). The **trusted-directory capability (issue #96)** lives here too, in the Tool Domain beside the other resolver seams: a recurring external root (a personal vault, a shared docs tree) had no standard tool surface, so the only workaround was raw `System.IO` inside `exec`, which bypasses the read tool's line ranges, gutter format, and freshness policy. `TrustedDirectoryPathResolver` is a DECORATOR over whatever resolver a tool already holds — it asks the wrapped resolver FIRST and returns its success unchanged, so workspace (or unrooted) semantics are exactly what they were; only a REFUSED ABSOLUTE path is reconsidered, and only against the approved roots, which keeps it a widening and never a change (with nothing approved it is byte-identical to the resolver it wraps, refusal text included, pinned by test). Roots are normalized once (trailing separators stripped) and compared case-insensitively and SEGMENT-AWARE, so a sibling whose name merely shares a prefix is outside. An approval grants READING; an entry's `editable` flag additionally grants writing, and a read-only root refuses writes with the distinct `TrustedRootReadOnly` code (read-only tools reach it through `AsReadOnlyResolver`, so a read is never refused as if it were a write). A path in no approved root keeps the wrapped `PathOutsideWorkspace` code with the approved list APPENDED, so the model learns what IS reachable. NAMED DECISIONS: approvals are WORKSPACE-scoped only (`trusted_directories:ws:{root}` — a global list would silently widen every other workspace's reach the moment one approved); anchoring drops the trusted set (an anchor is a narrower confinement boundary, and silent inheritance would let a spawn widen its own reach); and container-format tools (`docx`, `pdf`) resolve their one path by ACTION through `ActionScopedPathResolver` — a read-only action (`docx read`; `pdf read`/`render`) takes the read view, every other action including an unknown or absent one keeps the strict resolver, so a new action is mutating until named. The list parses strictly (`TrustedDirectoryPreferences`, `{path, enabled, editable}`, `editable` absent means read-only) and a parse failure resolves to NO roots — the safe direction for external reach is nothing, never half a list nobody can audit. `TrustedDirectoriesPromptProvider` names the approved roots in the system prompt (rendering EMPTY, and thus dropped by the composite, when nothing is approved, so a session with no approvals keeps a byte-identical prompt) because an approval the model cannot see is one it will never use. `TrustedDirectoriesCarrier` + `AgentSettings.TrustedDirectories` carry the workspace preference into the host process — which runs EVERY production turn — exactly as the session-file and skill-directory lists do. | Storage access is a capability the domain requests, not a technology it depends on. |

Both are named explicitly rather than pattern-matched, because `%selection%` would eventually eat a live key. It runs in `DesktopHost.PrepareAsync` on every app start: a delete leaves no marker to remember, so the second run simply finds nothing, and the APP is the only writer that migrates — the guest child host must never sweep against a file the app may be writing. **A MEMBER-LEVEL SWEEP EXISTS FOR A CONTAINER THAT SURVIVES** (`DeadMembersByKeyPrefix`): when a feature is one MEMBER of a payload that still carries live sections, deleting the whole row would destroy settings the user still wants, so the named member is stripped from the JSON in place and reported as `<key>#<member>`. The live case is `provider_settings:*#routing` (provider routing was deleted): the row survives because it still holds server_tools, plugins, and reasoning_summary. A payload that cannot be parsed, or that is not a JSON object, is LEFT ALONE and not reported — corrupt storage is an infrastructure fault, and a cleanup that rewrote it would destroy the evidence a human needs. A payload carrying no dead member is not rewritten at all, so a clean row never moves its `updated_at`. A sweep failure is reported and startup proceeds; a cleanup is never a reason to refuse to start. The `agent_events` append-only log (already the home of spawn/complete domain events) now also carries the REASONING telemetry trace (issue #263: `type = "reasoning"`, `AgentReasoningRecorded` payload keyed by agent + turn id + iteration), written best-effort through the Agent Domain's `IAgentEventLog` seam by the same `SqliteAgentStore` instance — no schema change, and no read path back into a request. `IModelCatalogCache` (interface in the Model Domain, like the file-system seams) persists each provider's fetched model catalog (`model_catalog_cache`, migration V17, one row per provider + resolved models endpoint; bound to a path that STILL EXISTS → this directory is a COPY (D6, fresh identity minted, notice shown, so two directories never share one record set). The alternative was asking the user a question the harness can already answer. **Root turns over the transport.** Two envelope kinds ride the same
framing and pumps as the child-run kinds: `root-turn` (app → host: `RootTurnRequest` =
turn id + input + seed) and `root-turn-event` (host → app: `RootTurnEvent` = turn id +
kind + payload + generation). The event kinds are a STRICT set — `delta`, `reasoning`,
`notice`, `tool`, `settled`, `progress`, `session-request`, and `context`; an unknown kind
is a protocol error, never a forward-compatible unknown. `context` carries the loop's
`OnContextUpdate` snapshot (`RootTurnContextPayload`: last input tokens, session totals,
catalog window, utilization, and the estimated bucket breakdown) so the status bar's CTX
line advances for a HOST-run turn exactly as it did in-process — the accountant lives in
the host, so a snapshot that did not travel left every production session's CTX frozen
(issue #255). A `tool` result payload is a JSON object carrying the tool's name, status, rich title, summary, FULL content, and its IMAGES (`RootTurnToolResultPayload.Images`, issue #230 — every conversation runs in a host process, so an image that does not ride this payload can never be rendered; absent means empty, so an older host's payload still parses). `RootTurnProtocol` is the codec; `RemoteAgentRuntime
.SendRootTurnAsync` is the app-side call and `ChildHostServer` the host-side case. The host
**must echo the request's generation verbatim** — the app drops any event whose
(id, generation) does not match the live turn, which is what keeps a reused turn id safe.
Turns are bounded by `RootTurnBudget` (idle bound that resets on every event, a separate
hard ceiling, and a separate generous SEND bound — never the idle window, because a lapsed
write is cancelled and a mid-frame cancellation is unrecoverable). The idle bound measures
LIVENESS, not busyness: the host HEARTBEATS (a `progress` event) whenever a turn has been
quiet, because a long tool call (an exec script, a subagent wait) emits nothing at all —
the app used to read that silence as a dead host, fail a HEALTHY turn, and abandon it while
the host kept running it, and that abandoned turn held the host's turn gate, so every
later turn queued behind it and failed the same way (the session was unusable from the
first error onward, 2026-10-22). The heartbeat interval is a quarter of the window the app
enforces, and the window rides the request (`RootTurnRequest.IdleTimeout`) so the two can
never disagree. An ABANDONED turn is also RELEASED: the app tells the host to stop the
turn it is no longer waiting for (`InterruptRootTurn`), so the gate is freed and the next
turn runs. A bounded send is
CANCELLED rather than abandoned, so the write gate is released; and because the frame header
and payload are two stream writes, a cancellation that interrupts a frame leaves the peer's
frame stream permanently desynchronized — `TransportFraming.WriteAsync` reports that as
`TransportFrameInterruptedException`, and the runtime answers it with `MarkConnectionLost`,
tearing the connection down and completing every pending root-turn waiter and child settle
with a declared failure instead of leaving a silently dead connection that still reports
itself alive. Configuration: the single preference key `subagent_root_turn_idle` (a
constant-format duration) → `SubAgentConfiguration.Bind` → `SubAgentOptions.RootTurnBudget`.
There is deliberately NO total-duration ceiling (issue #248): a wall-clock cap on a whole turn
killed legitimate long work — big investigations, long test runs, waiting on subagents — with
nothing to resume, so the idle window (liveness, reset by every event and by the host's
heartbeat) and the send bound (one frame on the wire) are the only two bounds, and a turn runs
until the host settles it or the caller stops it. `TurnCeilingExceeded` no longer exists. The
host RUNS the
turn (`RootRunHost`: the container's own `SendMessageCommandHandler`, so the conversation the
model reads is the host's), and it answers a turn it cannot run with a typed settle that
NAMES THE REAL CAUSE — "not bound to a root session (the host settings named no root
session id)" for a missing binding, "(<reason>)" for a container that could not be built.
The previous build swallowed that exception and reported the binding instead, so a locked
database read as a wiring fault (2026-10-22). A host whose deployment is incomplete (its
dependency manifest missing — a publishing app copies a referenced project's assemblies
but not its `deps.json`) says so at the same place, with the root cause under it
("DllNotFoundException: Unable to load DLL 'e_sqlite3'").

**Starting a new session is a REQUEST the app answers, and the tab is replaced IN PLACE
(issue #234).** Two more kinds ride the same framing: `session-request` (host → app, a
`RootTurnEvent` whose payload is `SessionRequestPayload` = request id + prompt + optional
handoff summary) and `session-response` (app → host, `SessionResponseCommand` = request id +

tab.** `MainViewModel.StartNewSessionAsync` (the user's `/new`) refuses while a turn runs
(`TurnBusy` — replacing the session would dispose the container under the running turn),
creates, and swaps the tab at the SAME index, firing the prompt as the new session's first
turn; the old session is completed gracefully first, so the Sessions dialog can still resume
it, and its container is disposed (which kills its host process).
`MainViewModel.HandleSessionRequestAsync` (the tool/handoff path) ANSWERS FIRST — the host
is blocked — and only then swaps, waiting for the requesting turn to go idle because the
host emits the request from inside its own turn. Every refusal path answers with its typed
code (`TabClosed`, `SessionRequestPending`, `SessionLaunchFailed`, `SeedUnsupported`); an
unanswered request is a tool waiting out its whole budget for an answer that was never
coming, and a second request while one is pending is refused rather than queued (two
launches racing for one tab slot would leave one session alive in no tab at all). A tab that
closes during the wait disposes the session it asked for instead of leaking it.

The compaction handoff (`compaction_handoff_enabled`, default OFF) rides the same channel:
`DefaultContextCompactor` returns a `CompactionOutcome.Handoff` instead of compacting in
place, the loop ends the turn with the named handoff line, and `RootRunHost` emits the
request with an EMPTY prompt (seed-only — a handoff continues from the summary, it does not
re-ask) and the summary. `SessionHandoffSeed` owns the seed shape: a System message flagged
`IsSummary` (the shape every surface already understands) under a prefix that says the
session CONTINUES from an earlier conversation rather than claiming a compaction that never
happened, and the factory persists the seed rows explicitly (the transcript sink's baseline
counts the seeded prefix as already-persisted, so without that a resume would lose it). A
blank summary seeds nothing, and a host with no seeded creator refuses the handoff
(`SeedUnsupported`) instead of silently dropping the summary it exists to carry.

A special seam sits beside the ACLs: `eThangAgent.Provider.Wire`, the shared Responses-API wire core (request `input`-item building, flat function-tool translation, non-streaming `output` parsing, and typed-event SSE stream application) consumed by the provider ACL. It exists because that logic is OpenAI Responses-wire plumbing while living entirely outside the domain. The doctrine this refines: ACLs share no **domain** code; provider wire plumbing may live in a shared infrastructure project.

## Technology Stack & Constraints

- **Runtime**: .NET 10
- **Language**: C#
- **Platform**: Windows only — all path handling, process execution, and scripting assume Windows.
- **Exec / Scripting**: Roslyn C# scripting via the Exec ACL (`IExecEngine`) — no PowerShell anywhere in the solution. External processes (e.g., `git`) are spawned directly with native .NET `Process` APIs.
- **AI Providers**: OpenRouter — the domain model speaks in provider-neutral concepts, and each provider's ACL implements them. Sessions are wired exclusively for one provider; switching providers is a different experience by design.
- **Interface**: Desktop (Avalonia)

### Packaging & Wiring

- Each domain and ACL is its own project (package) for composability.
- Packages are designed to be swapped or extended — replacing an ACL implementation must never require touching domain code.
- Dependency injection wires implementations at the composition root; domains depend only on interfaces and contain zero DI container references.
- `eThangAgent.ComputerUse.Host` is the supervised broker executable: it serves the computer-use NDJSON pipe, walks UIA trees, captures frames, and injects input — the killable native side of the ComputerUse ACL.

## Domains

The row also carries the usage ledger's price and attribution (issue #22): `CallClass` (`UsageCallClass` — the closed set `main_loop` | `compaction`, a NULL class reading as `main_loop` because every row written before the class existed came from the loop), `WorkspaceId`, `Provider`, and the three nullable prices `PromptPricePerToken` / `PromptCacheReadPricePerToken` / `CompletionPricePerToken` and `ModelId` (issue #24 — the per-model rollup groups on it; a row that cannot name its model is reported with a null model rather than attributed to one that did not run). PRICE IS STAMPED AT WRITE TIME because `model_catalog_cache` keeps one current row per provider and no history — a call not priced when it happens is unpriced forever, and a read-time join would silently re-price history. Every added member is nullable so an already-stored payload deserializes into the extended record with them null (pinned against a real legacy payload). Absent collaborators mean byte-identical legacy behavior. **The row also carries MEASURED LATENCY (issue #292): `DurationMs` and `FirstTokenMs`**, both nullable and both measured by the provider ACL — the only layer that sees both ends of a call — around the PROVIDER CALL (dispatch to settled), never the iteration, which would mostly measure our own tool dispatch and local work. The two are different facts: a provider that streams its first token in 300 ms and finishes in 40 s feels nothing like one that thinks for 20 s then dumps everything. NULL IS 'NOT MEASURED' AND ZERO IS A REAL MEASUREMENT — a call that finished inside a millisecond reports 0, and a non-streaming response reports `FirstTokenMs` null because it has no first delta to time; coercing either into the other would make a fast provider indistinguishable from an unmeasured one. The same row carries `ServedProvider`, which is **null in practice and that is the honest answer**: measured 2026-10-27 across six live models (routers included), pinned and unpinned, streaming and not, the Responses wire names no provider — no `provider` member in the body, no `X-Provider-Name` header — so the member is parsed for a wire that might start naming one and is NEVER backfilled from the request's pin, because a request's intention is not a fact about what served (the rule `ServedModelId` already follows). `Provider` remains what it always was: the provider whose PRICES were stamped. The summarizer call records the same timing through `CompactionOutcome.SummarizerTiming`/`SummarizerServedProvider`, so compaction rows stay comparable with main-loop rows. The RECORDING SITES are the loop's existing safe point (issue #23): `RecordUsageTelemetryAsync` — never `ReportUsage`, which returns early with no context monitor wired and would silently record nothing — writes one `main_loop` row per completed provider call (streaming and non-streaming reach the same point, so they are one code path), and the loop writes one `compaction` row per successful compaction INCLUDING a handoff outcome (the summarizer was called and billed either way), naming the SUMMARIZER's model and provider from `CompactionOutcome.SummarizerModelId`/`SummarizerProvider` — the resolved writer, the serving model on fallback, and null for the tail-compression fallback that makes no summarizer call at all. Before #23 `SummarizerUsage` was produced and read by nothing in production: summarizer spend was measured and thrown away. A record the domain REJECTS (`AgentUsageRecorded.Create` validates, rejecting negative counts as `InvalidUsageCounts`) or a store that faults is COUNTED and surfaced ONCE per turn as a `[usage ledger]` notice — a drop is never silent, but it is never turn-failing either, and the notice goes to the display channel so no request byte changes. The READ half (issue #24) is `IUsageQueries` (Model Domain) + `SqliteUsageQueries` (Storage ACL) over those same rows on the read-only connection: session totals, per-call-class totals, and per-model totals. SESSION ATTRIBUTION IS A RECURSIVE WALK, NOT A STAMPED COLUMN — a child stamps its OWN id as its session id, so a `session_id = root` filter would omit every subagent's spend; a `WITH RECURSIVE` CTE seeded with the root id follows `agents.parent_id` down and the usage rows join onto that subtree (verified on live data: all 1,835 usage rows attribute to a depth-0 root, zero unattributed, and it works retroactively for rows already written). The CTE seeds the root id DIRECTLY rather than selecting it from `agents`, so a session whose own row is missing still reports the rows it did record, and `UNION` (not `UNION ALL`) keeps a corrupt parent cycle from looping forever. THE CHARGE IS THE PROVIDER'S REPORTED `usage.cost` (nullable `TokenUsage.ReportedCost`), parsed from both streaming terminal and non-streaming responses and persisted on `AgentUsageRecorded` and `UsageRow`. A new row with no valid nonnegative reported charge is UNPRICED, even if catalog prices exist; zero is a real reported charge. Legacy rows without the `ExpectsReportedCost` marker retain the former `UsageCost` catalog-price estimate, counted as `EstimatedCalls` and marked `~` in the status bar; partial totals also carry `~` and report unpriced calls. The status rollup never presents an estimate as a confirmed charge. THE STATUS BAR'S SESSION COST rides a `usage` root-turn event kind (the closed strict set gains one member on both sides — app and host ship as one build, so no negotiation): the ledger row is written in the HOST process, so the in-process callback path cannot carry it. `TurnCallbacks.OnUsageRecorded` fires only AFTER the row is persisted (a total that counted a call the ledger dropped would disagree with the rollup the next tab open seeds from), `RootRunHost` emits `RootTurnUsagePayload`, and `StatusViewModel` seeds from `IUsageQueries` at tab open then advances event-driven — no polling. Three rendering states are deliberately distinct: priced spend shows money (`$0.0008` below a dollar, two decimals above), an unpriced session shows its token total instead (`12.4K tok`), and a session with no rows shows nothing — a cost of $0.0000 for spend nobody measured is the same lie as an overstatement. The in-memory `ContextAccountant` still starts at zero on a rebuild; the ledger rows are what survive. Server-side tool calls the provider executes inside its own response (web_search, web_fetch, image generation) never enter the message history, so the loop SURFACES them: one System line per call (`[<tool>] <detail>`, each result URL beneath) that also lands in the conversation so a resumed session sees it. An `openrouter:image_generation` call's artifact is PERSISTED first (issue #230): the wire carries it under `result`/`imageUrl` as a `data:<media>;base64,<payload>` URL (never under `action`, where the search/fetch detail lives), `ServerToolCallImage` carries it provider-neutrally (media type + payload), and the loop writes the bytes into the workspace through the Tool Domain's `IServerToolImageStore` seam — `.ethang/images/` under the session workspace, or under a child's ANCHOR when it has one, because a generated image belongs beside the work that produced it. The surfaced line then NAMES the saved path, and the image rides the `OnToolResult` callback so the Desktop renders it through the same surface computer screenshots already use. The store SNIFFS the format from the decoded bytes rather than trusting the wire's media-type claim, bounds size by `ImageLimits.MaxBytes`, and refuses anything but PNG/JPEG; every refusal is a typed error ON THE LINE, never a silent skip. RECORDED DESIGN DECISION — the artifact reaches the MODEL as a path, not as an inlined image part: the Responses API's `Message` input shape accepts `input_image` only on user/system/developer roles (an assistant message cannot carry one, so relaxing `Conversation.NormalizeParts` would emit a wire shape the provider rejects), a synthetic tool result is unattributable (`function_call_output` needs a `call_id` from a `function_call` item), and inlining a 1024x1024 PNG costs 1.3-2.7 M base64 characters re-sent on every later request. The path costs a dozen tokens and `read_image` pulls the bytes on demand, so the line names the path and — gated on `ModelConfig.AcceptsImageInput`, so a text-only model is never invited to call a tool that would fail — says `read_image` can open it.
- **Chain Domain (record)**: the durable EXECUTION record the harness owns (issue #300) — `chains` + `chain_steps`, migration V23, `IChainStore` in the Agent Domain and `SqliteChainStore` in the Storage ACL. **A chain is a SIBLING of the plan, never a field set on it (D1)**: the plan's writer is a model judging what is done, the chain's writer is the harness advancing a cursor, and one table with two writers and one CAS version could not tell which refusal came from whom. **It REFERENCES the plan and never copies it (D2)**: `plan_id` plus the `plan_version` it started at, so titles and details are read at brief time (a plan edit reaches the next step with no sync) while the recorded start version keeps a later revision VISIBLE without being retroactive. **A step's EXECUTION state lives on the chain, not on the step (D3)** — position, status, assigned session, attempt count, outcome, actor, and the claim clock — because a plan step says what should be true and a chain step says what happened; a `Done` plan step with three failed chain attempts is a coherent, truthful state and collapsing the two would lose it. **The statuses are the minimum the lifecycle needs (D4)**: chain `Running | Parked | Completed | Abandoned`, step `Pending | Running | Done | Failed | Skipped | Parked`. `Parked` is load-bearing rather than decorative — failure handling parks instead of aborting, so the record must be able to say 'waiting' without claiming failure — and `Skipped` is the truthful exit that keeps the completion invariant honest in both directions: `ChainStatusTransition` refuses `-> Completed` while any step is unsettled (naming the offending positions and statuses) and leaves `Abandoned` ungated, because dropping a half-finished chain is the honest way out. **Attempts are counted per step (D5)** and the count is the only bound on a session that keeps failing the same way; a retry RESUMES the same session, so the count is what a cap reads. **Every transition carries its ACTOR (D6)** — a typed `ChainActor` (`harness` | `user` | `session <id>`), never a nullable session id, because the harness advancing a chain has no session and 'which session decided to start the next one' must be answerable with the honest answer 'none of them'; the three documented shapes are the only ones that parse, so a corrupt actor column is a REPORTED row rather than a silent read as the harness. **A `Running` step's claim EXPIRES, it is not detected as dead** (`ChainClaimPolicy.ClaimTtl`, one hour, following Agensh's `DEFAULT_CLAIM_TTL_SECONDS`): this database's history holds 128 child rows marked Running with no run behind them, every one a claim nothing would ever retract, and a TTL answers by construction where a liveness probe needs someone to ask. Expiry is computed ON READ from `ClaimedAt` — never written by a sweeper, so a crashed process cannot leave a claim alive and a sleeping one cannot expire a live claim early — and a Running step with NO clock reads as lapsed rather than as an eternal claim. The TTL is a NAMED CONSTANT with a test pinning it, deliberately not a settings key: a configurable claim window is one that can be set to never expire. Both status columns carry CHECK constraints (the V20/V21 precedent), so a DIRECT writer — an exec script's SQL — cannot smuggle an out-of-enum value, and `AppDatabase.LatestSchemaVersion` is declared once with a startup guard that refuses to migrate when the table and the constant disagree, so adding a migration without updating it is a named failure rather than a half-migrated database.
- **Chain Domain (durability, issue #317)**: the record survives its workspace. `workspace_id` is a stable identity (see the Storage ACL row), so a moved workspace keeps its chains and a deleted one leaves them ORPHANED rather than gone — `ChainOrphanQuery` reports them through the read-only `IChainWorkspaceQuery` port, which crosses workspace boundaries by definition and is therefore never a widening of `IChainStore`. Retention (#246) must never delete an orphaned chain (D8).
- **Chain Domain (the mechanical advance, issue #301)**: a completion fact STARTS the next session, and no model decides whether to continue. The trigger is `PlanChangedEvent` with `Change == "steps"` — the fact the Composition's `PlanChangePublisher` already raises and the host already forwards over the wire — never a poll, which would re-derive what is already published and race the write. `ChainAdvancePolicy` is the PURE rule (facts in, decision out, no I/O and no clock): a foreign step is refused naming the session that IS assigned, a LAPSED claim is refused with its own code (the #300 amendment), a step that is not Done is refused, and otherwise the cursor advances to the next available step or completes the chain. `ChainAdvanceService` (Agent Application) enacts it through `IChainAdvanceHost`, and ORDER IS LOAD-BEARING: the completed step is settled and the next step CLAIMED before the old session is closed and the new one started, so the successor's ownership check passes and the chain never has a step with no owner. The claim needs a session id that does not exist yet, so it is taken under a placeholder and then REASSIGNED (`Chain.ReassignStep`) — deliberately not a second `ClaimStep`, which would increment `Attempts` and restart the claim clock for an attempt that was never made; a failed launch `ReleaseStep`s the claim while KEEPING the attempt, because a launch that failed is still an attempt the bound must see. A refusal leaves the session OPEN (the model must be able to read why and correct itself) and closes it only on a real advance — and a sequential advance closes it by REPLACING it, so the service does not also close it (that would tear one session down twice). **OWNERSHIP IS ENFORCED AT THE WRITE (D3)**: `PlanCapabilityProvider.update-step` consults `IPlanStepOwnershipGate` before writing a `Done`, and the Composition adapts the chain record to it (`ChainStepOwnershipGate`) — the `IPlanCompletionGate` precedent, because the answer lives on Agent-domain surface the Plan Domain must not reference. A session executing NO chain step passes straight through, which is what keeps the ordinary way a plan is worked intact; `Skipped` is never gated (it is the truthful exit #271 depends on), and the plan id must match too, since a position alone is not an assignment. **ROOT SUPERVISION IS NEW MACHINERY (D5), not a reuse**: nothing today mints a supervisor for a root (`ChildSupervisor`s are minted per CHILD RUN inside `BeginRun`, the watchdog sweeps `DescendantsOf(rootId)` whose walk starts from `ParentId` so the root is never in the set, and orphan repair exempts the root explicitly). `RootSessionSupervisor` holds the idle clock and `RootSessionWatchdog` (an `IWatchdogTicker`) enacts `RootSupervisionPolicy` — nudge once, then PARK the chain, never `Failed(Hung)`: a parked chain is waiting for a human and a failed one is broken. **THE CLOCK IS RE-SOURCED**: its input is `RootTurnActivity` (turn started / tool started / streamed / turn settled), facts the ROOT loop already produces and which `AgentSessionViewModel` now emits through `AgentSessionViewModelOptions.RootActivity` — NOT `ChildProgressEvent`, which describes a child run and is retired by #305/#316, and NOT a wall-clock timer, the mechanism `ChildTimeout` was deleted for. A nudge that cannot be delivered spends NO attempt (one dead host would otherwise park a chain a human never got the chance to unblock), and the nudge text is NOT `WatchdogPolicy.WrapUpNudge`: that asks for a final REPORT, while a chain step owes a COMPLETION. `IChainStore.FindBySessionAsync` answers 'which chain step is this session executing' in one indexed query, because the completion fact carries only the authoring agent id. **`agent.*` ACTION CLASSIFICATION (recorded on #301 before the code changed)**: kept — `status`, `result`, `cancel`; retired by #316 — `send`, `receipts`, `route`, `escalate`, `notify-subtree`, `notify-ancestors`; retired with no owning issue yet — `spawn`, `wait`, `fanout`, `resume` (#305 retired the in-process RUNTIME without retiring the TOOL, and #316's dead list omits them; #308 is the nearest home and this issue does not invent one).
- **Chain Domain (creation, issue #313)**: the plan-to-execution transition — the hinge the design pass missed, because everything else assumes a chain already exists. **THE TRANSITION IS AN EXPLICIT ACTION (D1)**: a plan can exist indefinitely without becoming a chain (a design artifact someone is still arguing about), so `chain.start` is the statement 'execute this'. **IT LIVES IN A NEW `ChainCapabilityProvider` IN THE AGENT DOMAIN (D6), NOT the Plan provider** — putting it there would make the Plan Domain reference the Agent Domain, and the chain record is Agent-domain surface anyway. **THE ACTION IS `start`, NOT `create`, and that is load-bearing**: capability action names are GLOBALLY unique (the registry dispatches by bare name) and the Plan provider already owns `create`, so the collision was a startup failure — `Duplicate action name 'create' across capability providers` — caught by the E2E suite rather than by review. `start` is also the truer name: the action does not merely write a record, it converts a plan AND starts step 1. **ROLES ARE DECLARED AT CREATION (D2, parent D15)** and the vocabulary is exactly `implement | review` (D7): `ChainStepRole` carries the kind plus, for a review step, the reviewer's model — and the model is NOT required here, because #218's separation rule refuses a review step that omits it AT SESSION START, where the implementer's model is known and separation can actually be evaluated; creation could not check separation against a model it has not resolved. A `model` with no `role` IS a review declaration (stating one is the declaration; requiring `role=review` too would ask the caller to say it twice), while `role=implement` WITH a model is refused rather than ignored — silently dropping it would leave the caller believing a constraint was recorded. **NOT EVERY STEP BECOMES A CHAIN STEP (D3)**: `steps` names the ones that execute; omitting it means 'execute the whole plan', which is the common case, so the declaration is the control and the omission is the shortcut. **VALIDATION IS TOTAL AND PURE (`ChainCreationPolicy`, D4)**: `ChainNoExecutableSteps` (D10 — an empty chain that immediately reports `Completed` is a lie about work that did not happen), `ChainStepMissing` (naming the missing positions AND what the plan does have), `ChainStepRoleConflict` (one position, two roles), `ChainPlanUnreadable` (the plan could not be read, so nothing was validated against it — re-reading is the remedy, not editing the declaration), and `ChainStepCannotCreateChain` (D9 — a session executing a chain step may not start a chain; the check reads the chain record, because the record already answers 'which step is this session executing' and a second source of that answer could disagree). **THE CREATING SESSION IS NOT THE OWNER (D5)**: creation claims step 1 for a session that does not exist yet, starts it through `IChainStartPort`, and REASSIGNS the claim to the real id — the #301 advance's order, applied at creation, so the claim is held during the launch window and spends no second attempt. A failed launch RELEASES the claim (keeping the attempt) and LEAVES THE CHAIN CREATED: the record is a fact about the plan, the launch is a fact about this process, and deleting the chain would destroy a record the user can resume from. **THE LAUNCH RIDES THE EXISTING `session-request` ENVELOPE**, not a second kind: the act is identical to `new_session` (start a session in this workspace and answer with its id), so `SessionRequestPayload` gained an optional `ChainStep` assignment and the app renders the brief and starts the session SEED-ONLY — a second envelope kind would be a second codec and a second handler for one behaviour. **THE ROLE TRAVELS FROM THE RECORD, never from the declaration**: `ChainStepAssignment.Role` is read from the chain row by both launchers (creation and the #301 advance), because the record is the only source a resumed or restarted launch also has. **`Chain.NewFromSeeds` IS NAMED, NOT AN OVERLOAD** of the position-only factory: an overload differing only by element type makes a collection expression ambiguous, and two names say which one is meant. **Migration V26 adds `chain_steps.role` + `role_model`** (both CHECK-constrained closed sets, the V20/V21/V23 precedent), rebuilding the table the V20/V21/V24 way and backfilling every existing step as `Implement` — there was no review step to have recorded — while V23 creates the columns too so a fresh database walks the same path and the two cannot diverge.
- **Chain Domain (the review step, issue #306)**: the role a chain step was assigned is now ACTED ON, not just recorded. #313 shipped the declaration (`ChainStepRole.Review`, the `role`/`role_model` columns, `role=review` on `chain.start`) and nothing consumed it: the role crossed the wire on `SessionRequestChainStep` and `MainViewModel.SeedForAsync` rebuilt the assignment with `null`, so **every review step's session was seeded as an implementer** — handed `plan.update-step ... status=Done` as its completion contract, which is the one instruction a reviewer must not receive (it would finish the work instead of judging it). The role now survives the launch (`ChainStepRole.TryDecode` with an unparseable token degrading to `Implement`, the same default the record applies rather than a failed launch) and **the brief and the contract both branch on it**: `ChainBriefRenderer` and `ChainContractRenderer` each render a review section instead of the completion section. BOTH must branch, and that is not redundancy — the brief is a seeded MESSAGE a compaction can evict, while the contract is in every request, so a reviewer that read the right instruction only in its first message would drift back to finishing the work. The review brief states the verdict shape (`approve | deny | approve-with-conditions`) and the citation rule, and **the rubric is #217's, so its absence is STATED rather than invented**: `ChainBriefFacts.ReviewRubricAvailable` is a fact the composition answers from the SAME `ISkillCatalog` the session's skill listing is built from (the two cannot disagree about whether a rubric exists), so the brief names `reviewing-plans` as the rubric when the skill is installed and says plainly that none is available when it is not — a fabricated rubric is a verdict nobody can compare. **That fact flipped to true with NO code change when the skill shipped (#217)**, which is the whole point of asking the catalog instead of assuming: `ReviewRubricAvailabilityTests` asserts the real source over the real catalog and the rendered instruction together, so the seam cannot silently regress to 'no rubric'. **THE RUBRIC IS READ ONLY WHEN SOMETHING USES IT**: an implement step never touches the skill catalog, so a chain with no review step costs exactly what it did before, pinned by a test on the read count. An implement step's brief and contract are **byte-identical** to the pre-#306 text (pinned by test), because the change is a branch on role and not a rewrite of the implementer contract. The verdict is a TYPE now (`PlanReviewVerdict`, #216) but a review step does not yet WRITE one: `ChainStep.Outcome` is still free text, so a review step settles `Done` carrying its verdict and findings in the outcome, and the typed record is written by the deny path (#219/#320). #218's separation rule reads the role this issue makes survive.
- **Chain Domain (the contract in the system prompt, issue #311)**: `ChainContract` is the STANDING facts of the chain a session executes — chain id, plan id, step position, ledger key, and the workspace's gate commands — and `ChainContractRenderer` is the PURE render of them (no clock, no I/O, no counter: the prompt is the first bytes of every request, so a drifting sentence would invalidate the provider's prompt cache from its first changed character, #267). `ChainContract.For(ChainBriefFacts)` is the ONE derivation site, so the ledger key the prompt names and the key the brief names are one value rather than two that happen to agree; `ChainLedgerSlug.KeyFor(title)` derives `sci.<slug>/ledger` once for both. The provider (`ChainContractPromptProvider`, Composition) renders EMPTY for a session outside a chain — the `TrustedDirectoriesPromptProvider` precedent, and the whole mechanism, because the composite drops empty entries — so a session a user started by hand keeps a byte-identical prompt, pinned by test against the composite the composition actually builds. **THE CONTRACT RIDES THE SETTINGS JSON** (`AgentSettings.ChainContract`, filled from `ChainContractCarrier` at container build, overlaid by the RemoteHost block): the HOST builds the system prompt for every production turn, so a contract resolved app-side and never shipped would leave the prompt silent in the only process that serves the model. It is a per-CREATE parameter (`AgentSessionFactory.CreateAsync(..., chainContract, ct)`), never factory state — the factory serves many sessions over one workspace, so a contract held on it would be one session's identity leaking onto every other. `ChainBriefService.BuildLaunchAsync` returns the seed AND the contract from ONE gather (`ChainBriefLaunch`), and the Desktop's `SeededSessionCreator` carries both, so a caller cannot seed one and forget the other. **IT CARRIES NO PROCEDURE**: the chain skill (#308) says how to work, the contract says what the session IS — two statements of one rule drift, and the prompt is the worse place to keep the copy.
- **Chain Domain (reviewer separation, issue #218)**: a review step's session must RUN ON THE REVIEWER'S MODEL, and that model must differ from the implementer's. `ReviewerSeparationPolicy` is the PURE rule (facts in, refusal out, no I/O, no clock) with two named codes: `ReviewerModelMissing` (D1 - a review step that names no model cannot be compared at all, so it is refused before the match is even considered) and `ReviewerMatchesImplementer` (D4 - a typed refusal, never a silent substitution, because swapping models quietly would make the review's provenance a lie). **THE COMPARISON IS AGAINST THE CHAIN RECORD, NOT A LIVE PARENT (D3)**: the #215 version compared a child's resolved model to its parent's config, which is unavailable after a restart and after the implementer's session closes. `chain_steps.served_model` (V28, nullable, NO backfill - a guessed model would fabricate a comparison the rule then acts on) records what each step's session ACTUALLY served, stamped by `ChainAdvanceService.RecordPredecessorModelAsync` from the agent row's `ModelUsed` (the `unassigned` sentinel and a blank id are 'not recorded', never 'no model'). **THE IMPLEMENTER IS THE NEAREST PRECEDING NON-REVIEW STEP WITH A RECORDED MODEL** (`ReviewerSeparationPolicy.ImplementerFor`): chain steps are independent (#299 D8, re-settled when #321 closed as not-a-defect), so the record carries no review-to-implementer link, and a review judges the work that came before it; a review step at position 1 has nothing to separate from. **THE COMPARISON IS ON THE RESOLVED ID (D2)** - `ModelVariants.BaseOf` strips the routing suffix, so `alpha/model:nitro` and `alpha/model` are one model and comparing request strings would pass a review running on the implementer's model - and it is case-insensitive. **TWO BOUNDARIES, ONE RULE**: `ChainCreationPolicy` refuses a review step with no model at DECLARATION time (the separation half cannot run there - the implementer's model does not exist yet - but the missing-model half needs only the declaration, and a chain that can never start its review step should not be created), and `ChainReviewerGate` enforces both halves at SESSION START. The gate **LOADS THE RECORD ITSELF** rather than trusting a caller's snapshot, and that is correctness rather than convenience: the implementer's model is stamped moments before, which moves the version, so a caller holding the pre-stamp snapshot would compare against an EMPTY model and CLEAR a step the rule should have refused. It runs BEFORE the claim at both launch sites (`ChainAdvanceService.StartStepAsync`, `ChainCapabilityProvider.CreateAndStartAsync`), so a refused review step spends no attempt and holds no claim; a MATCH parks the chain through `ChainService.ParkAsync` with the harness as actor and the step named (D5, parent D8 - waiting for a human, not broken), while a MISSING model is a typed failure that starts nothing. **THE MODEL ALSO HAS TO REACH THE SESSION THAT SERVES**: it rides `SessionRequestChainStep.Model` beside the role, `MainViewModel` decodes it into the assignment, and `ApplyChainStepModel` writes it to the live preference AFTER `RestoreSessionPreferencesAsync` (which overwrites that preference with the workspace's saved choice, so applying earlier would leave the reviewer on the implementer's model while the record claimed separation). Without that half the rule would be a claim about a session that never ran on it. An implementer step is untouched (D6/B6): it keeps the workspace's model choice, and the wire sends no model for it.
- **Chain Domain (scope note)**: the record row owns the schema, the status machines, the store, and the actor type; the advance row owns who moves the cursor (#301); the creation row owns the transition (#313); the contract row owns what a session is told it is (#311); the lifecycle row owns what happens when a step does not go cleanly (#303); the separation row owns which model a review step may run on (#218). The gate at step and chain level (#304) and the deny path (#219/#320) remain sibling issues and are deliberately absent here: building any of them now would be the workaround the chain skill's rule 5 forbids.
- **Chain Domain (lifecycle, issue #303)**: what a chain does when a step does not go cleanly. **D1 — A RETRY RESUMES, IT DOES NOT RESTART**: `ChainStep.Retry` re-enters a `Failed` step for the SAME session, refused for any other claimant (a different session has no transcript to continue from) and refused for any status but `Failed`. It deliberately does NOT go through `Claim`, which would increment the attempt count and restart the claim clock for an attempt that is a continuation. **D2 — THREE ATTEMPTS, COUNTED PER STEP** (`ChainRetryPolicy.MaxAttempts`, a NAMED CONSTANT with a test pinning it, following `ChainClaimPolicy.ClaimTtl` — a configurable cap is one that can be set to never fire). The boundary is the cap itself: `CanRetry(3)` is false, because the count is attempts MADE, not remaining. **D3/D9 — PARKING IS A FIRST-CLASS STATUS, NOT AN ERROR**, and every park names its reason and its step on the record (`park_reason`, `parked_at_position`); the RENDERING is #312's, which is why the criterion moved there. **D7 — A RESUMED STEP IS RE-ENTERED WITH A FAILURE NOTE, NOT THE WATCHDOG NUDGE**: `ChainRetryPolicy.FailureNote` names the attempt, the chain, the step, and what the failed attempt recorded, because the nudge is about IDLENESS and would tell a session something untrue about why it was restarted. **D5 — NO AUTO-RESUME ON RESTART**: no startup path reads chains at all (pinned structurally by `ChainRestartPolicyTests`, since the absence of a behaviour is not observable by running one), and `Chain.Resume` requires an actor so the record can always say a human un-parked it. **A BLOCKED CHAIN IS PARKED, NOT LEFT RUNNING** — `ChainAdvanceService` previously returned on a `Blocked` decision without writing anything, so a chain with a parked step and nothing left to start sat `Running` forever while every surface reported it in progress. **AN UNREACHABLE SESSION PARKS WITHOUT SPENDING AN ATTEMPT** (the `RootSessionWatchdog` rule): a resume that never landed did not fail the work, and burning the budget on it would park a chain a human never got the chance to unblock. The enactment lives in `ChainLifecycleService` over `IChainLifecycleHost` (Agent Application) — DISTINCT from `IChainAdvanceHost`, which closes a finished session and starts a FRESH one for the next step; this one RE-ENTERS a session that already exists, which is the whole point of D1. ORDER IS LOAD-BEARING: the step is re-entered BEFORE the session is resumed, so the record shows a live claim when the session starts working and an instantly-completing session is not refused by the ownership gate. `ChainStepStatus.Failed` was previously unreachable in production (the only settle was `Done`); the lifecycle is what writes it.

- **Model Domain**: model capabilities, provider contracts, model configuration, and MODEL + ROUTING-VARIANT resolution (`IModelCatalog`, `RootAgentResolver`, `SessionModelPreferences`, `ModelVariant`, `ModelVariantChoice`). **CATALOG TRUTH (issue #289)** lives here: `ModelProviderEntry`'s three prices are NULLABLE (`decimal?`) because "no price advertised" is a different fact from "this model is free" — the parser returned 0 for a missing pricing block, so an unpriced model was indistinguishable from a free one (measured on the live catalog: 20 rows serve zero prices, 3 of them are not `:free`). A null price means UNKNOWN, never free; a served `0` is a real price of zero; the routing pseudo-models' `-1` ("set at routing time") stays negative so a display surface can say `pricing varies`, while a null renders `pricing unknown` (a `$0` would tell the user a paid model is free). `SupportsTextOutput` is parsed from `architecture.output_modalities` (absent → false; a text+audio generator still resolves true — it is rejected elsewhere for its missing tool capability) and `IsRouter` from `architecture.tokenizer == "Router"` (27 live rows; the only signal that also covers the `~`-prefixed "latest" aliases, which an id-prefix test cannot). `IsAdvertisedFree` (both prices present and zero) and `HasAdvertisedPrices` are the two predicates consumers should use instead of comparing numbers. **ENDPOINT FACTS (issue #293)** extend the same truth discipline to four fields the parser used to discard and two it used to trust. `UptimeLast30m`/`UptimeLast5m`/`UptimeLast1d` are the reliability signal that IS populated (measured live: 35 of 35 endpoints on one model, 3/7 and 6/8 on two others) — a provider at 87% is a real risk to a long session in a way no price column can express. `SupportsImplicitCaching` is **TRI-STATE (`bool?`)** on purpose: a row from a catalog cache written before the member existed has said NOTHING, and coercing that to `false` would tell the user a caching provider does not cache — `false` is only ever a parsed `false`, and a model whose endpoints call failed keeps `null` rather than inheriting a fabricated one. `PromptCacheWritePricePerToken` completes the cost formula: a model whose cache READS are free but whose cache WRITES cost 1.25x the prompt price is not the bargain the read price suggests. `PriceOverrides` is a price LADDER and — measured against the live payload, correcting the parent issue's hypothesis — **its shape is a PROMPT-SIZE TIER, not a peak/off-peak clock**: every live entry carries `min_prompt_tokens` (200000 on Claude Sonnet 4.5, 272000 on GPT-6.1 Terra) and none carries a time bound, so the two prices the parent read as day/night are the two rungs of one ladder and a long-context call pays the upper one. `PriceTiers.Applicable` is a PURE function returning the HIGHEST applicable rung rather than the first (the API serves ascending today; trusting array order would mis-price the day a provider emitted it differently), and `ModelProviderEntry.PricesFor(promptTokens)` resolves it — so `IUsagePriceSource.PricesForAsync` takes the call's prompt size and `CatalogUsagePriceSource` **memoizes the ENTRY, not the resolved prices** (caching the price set would serve the first call's tier to every later call, silently billing a long-context call at the short-context rate). A rung that omits a price leaves it null rather than inheriting the base — a tier states different numbers, and inheritance would fabricate one. **THE PERFORMANCE FIELDS ARE KEPT AND DISTRUSTED**: `LatencyMs`/`ThroughputTokensPerSec` stay on the record and stay nullable (the provider may populate them later; removing them would be a lie in the other direction), but NO consumer treats them as a latency source — measured live across 5 models and 52 endpoints they were null on EVERY row, so a picker rendering them would print `0 ms` and tell the user every provider responds instantly. `ProviderPerformanceText` is the ONE contract that decides how an absent number is stated (`not measured`, never a blank or a zero) for latency, throughput, uptime, and cache discount, with a real `0` staying a real measurement — the same rule the nullable prices follow, pinned by test on both sides. `BestFreeModelSelector` is a PURE function over entries — free + text + tool use + context window + not-a-router, ranked by coding, then intelligence, then agentic with NULL SCORES LAST (an unmeasured model is not a zero-scoring one), ties broken by model id so a RECORDED pick is stable — and it exposes `Select` (the winner) and `Rank` (the whole order). **The ranked list is load-bearing, not a convenience**: measured 2026-10-26 the top two ranked free models answer every request with HTTP 403 ("only available on agentic harnesses"), so a caller that takes only the first pick can end up with no model at all; any future "best free" picker option and the live suite both walk the order. Criteria (`BestFreeModelCriteria`) are call-site knobs, never constants: the rule knows nothing about what a caller intends to send. **EFFECTIVE PRICE AND PROVIDER RANKING (issue #294)** are the two PURE functions a provider comparison is built from, so no surface can invent a second version that disagrees — the same precedent `UsageCost` set for the ledger. `EffectivePrice.Input(promptPrice, cacheReadPrice, cacheWritePrice, hitRate, supportsImplicitCaching)` returns an `EffectiveInputPrice`: the blended read cost `(1-h)*prompt + h*cacheRead` per input token, the cache-WRITE cost as a SEPARATE member (a write is paid once to populate a prefix, a read on every later call — blending them would need a read-to-write ratio this domain refuses to invent), the hit rate it was computed at (so no caller can show the number without the assumption), and a `CacheDiscountBasis` saying WHY the discount was or was not applied. **THE HIT RATE IS ALWAYS AN ARGUMENT, NEVER A CONSTANT**: a session at 97% and a session at 0% are comparing different providers for the same model. **D3 IS THE LOAD-BEARING RULE**: a provider whose `SupportsImplicitCaching` is not verified-true has NO cache discount whatever it advertises — `false` and `null` both withhold it, because a discount that will never be charged is exactly what the picker must not recommend (the tri-state is preserved: `null` reports `ImplicitCachingUnverified`, never a claim the provider does not cache). A missing price makes the result NULL, never zero; a served zero stays a real price; a negative advertised price is not a price. `EffectivePrice.For(entry, hitRate, promptTokens)` resolves the prices from the row's own price LADDER (issue #293) so a long-context call is compared at the rung it will be billed from, taking the cache-write price from the same rung. Only the INPUT price is blended — caching changes what an input token costs and nothing else, so `CompletionPricePerToken` is already the effective output price. `ProviderRanking.Rank(entries, RankingCriteria)` orders rows by a caller's `ProviderPriority` list — a `ProviderDimension` plus a DIRECTION, never a weight — as a LEXICOGRAPHIC sort: the first priority decides on its own and later ones are consulted only among rows the earlier ones tied, so no composite score exists anywhere in this domain (a caller that wants weights supplies them as its own normalization, and the picker's presets are that caller). **NULLS SORT LAST IN BOTH DIRECTIONS** (the null placement is applied BEFORE the direction, or a descending sort would float an unmeasured provider to the top and call it the fastest). **HARD FILTERS ARE SEPARATE FROM RANKING** (`ProviderFilters`: max effective input price, min uptime, min context window) and a row failing one is EXCLUDED, never ranked low — an unknown value fails a filter, since a provider whose price could not be computed cannot be shown to be within a ceiling. `RankableProvider` carries the caller's OBSERVED latency/throughput so ranking prefers our own measurement over the catalog's structurally-dead fields (issue #293), and `RankedProvider` carries the `EffectiveInputPrice` it ranked on so no caller recomputes it at a different hit rate. Ties fall to model id then provider name, so the same catalog and priorities always yield the same order; an empty result is an ANSWER (nothing met the requirements), never grounds to relax a filter the user set. The usage ledger's READ side lives here too (issue #24): `IUsageQueries` (session rollups over the persisted usage rows), the neutral `UsageRow`/`UsageTotal`/`UsageSummary` shapes, the ONE cost formula (`UsageCost`), and the `UsageTally` accumulator the status bar seeds and advances. **OBSERVED PROVIDER PERFORMANCE (issue #295)** is the second read model over those same rows, and it exists because the catalog cannot answer the question: `ProviderPerformanceAsync(ProviderPerformanceRequest)` returns a `ProviderPerformanceReport` of one `ProviderPerformance` per (model, provider) PAIR — median call duration, p90 duration, median first-token latency, median output rate, and the token counts the hit rate derives from — each with its own SAMPLE COUNT, because a median over three calls is not a median over three thousand (D1). **MEDIAN, NOT MEAN (D2)**: provider latency has a long right tail (a single 578-second call measured in this workspace would move a mean by seconds and describe nothing), pinned by test against exactly that fixture. **A CALL WITH NO OUTPUT IS EXCLUDED FROM THROUGHPUT (D3)**, never clamped to zero — a tool-call-only response has no rate, and letting it through would drag the median toward zero and call a fast provider slow; a zero-duration call is excluded for the same reason rather than reporting an infinite rate. **THE HIT RATE IS AN OUTPUT OF THE SAME QUERY AS THE ROLLUP (D4)**, derived by `UsageStatistics.HitRate` from the counts in scope, so the number the picker multiplies prices by and the number the status bar shows cannot disagree — the structural version of the `UsageCost` precedent. **SCOPE IS A FIXED FALLBACK CHAIN — session, then workspace, then global (D5) — AND THE REPORT NAMES THE RUNG THAT ANSWERED** (`UsageScope`), because a fresh session has no rows of its own and a projection built on an unstated scope is a guess wearing a decimal point; a request naming neither id is a NAMED FAILURE rather than an answer from the whole ledger. **A LEGACY ROW WITH NO `DurationMs` IS EXCLUDED FROM LATENCY AND COUNTED AS UNMEASURED (B6)**, never treated as a zero-duration call. The arithmetic lives in `UsageStatistics` as PURE functions (`Median`, `Percentile` — NEAREST-RANK, so a percentile is a duration some call actually took — `OutputTokensPerSecond`, `HitRate`), and the ACL aggregates in C# over the same rows the summary reads rather than in a second SQL implementation. `ProviderPerformanceReport.Rankable(entries)` is the SEAM INTO RANKING (issue #294's `RankableProvider`): measurements arrive as OBSERVATIONS, an unmeasured pair arrives as NULLS rather than zeros, and matching is by the PAIR so one provider's numbers never bind to another model's row. The read is capped (`PerformanceRowCap`, newest rows first) and a capped read SAYS SO (`Truncated`) instead of presenting a partial read as complete history. Context accounting lives here too: both ACLs report provider-scored `TokenUsage` on every response, `ModelConfig` carries a nullable `ContextWindow` — null means not yet catalog-resolved (bootstrap configs); every serving model's window resolves from the provider catalog through `IContextWindowSource` (no curated constants exist; OpenRouter's `openrouter/auto` is a fetched catalog row at its API-reported size), and a catalog miss fails the turn/spawn loudly (never a fabricated window), and `ContextAccountant` (`IContextMonitor`) keeps utilization against that window — provider usage reports are the only decision input; character-based numbers are estimates for UI breakdowns only. It also accumulates the two provider-scored numbers the reasoning-in-context work (#261) is measured with (#262): the prompt-cache hit count (`input_tokens_details.cached_tokens`) and the reasoning-token count (`output_tokens_details.reasoning_tokens`), both carried on `TokenUsage` and both NULL when the provider omits them — a reported `reasoning_tokens: 0` (reasoning that billed nothing) stays a different fact from no report at all, never coerced to zero — with the cache-hit ratio DERIVED on `ContextStatus` (`CacheHitPercent`) so no caller can hand in a ratio that disagrees with the counts it came from. The catalog's `ModelProviderEntry` carries a NULLABLE `PromptCacheReadPricePerToken` (issue #22) parsed from the endpoints API's `input_cache_read` at both the model and per-endpoint level — nullable because "no cache price advertised" is a different fact from "cache reads are free", and a negative advertised value (the routing pseudo-models' -1, "set at routing time") is not a price at all — and `CatalogUsagePriceSource` (`IUsagePriceSource`) resolves catalog reference prices a usage row stamps, memoized per base model for the process lifetime while a FAILED catalog read is deliberately not memoized (a transient fault must not poison every later stamp with nulls). Both ride the `context` wire payload as defaulted members (an older host's omission reads as unreported) so the CTX line's `, cache 82%, reasoning 1.2K` segments advance in a host-run session, and a provider reporting neither renders exactly the pre-#262 line. Model resolution is deterministic and preference-driven: the user's live model choice (via `SessionModelPreferences`) wins, then the session pin (the persisted `ModelUsed`, the record of what actually served) — and then NOTHING: a session that names no model FAILS the turn (`NoModelSelected`) and a named model whose catalog window is unknown FAILS it too (`UnknownModelWindow`). The harness never substitutes a different model: the user picked `minimax/minimax-m3.1-flash:free` and the turns ran on `openrouter/auto` (2026-10-22) — a silent substitution is a lie about what ran. The Desktop therefore always NAMES the session's model (the user's persisted pick, else the session's pin — the record of what actually served, so a resume continues with it — else the session's default), so the status bar and the model that serves are the same model, and the live choice RIDES the root-turn request (`RootTurnRequest.ModelPreferences`, opaque JSON decoded host-side) because the picker lives in the app while the conversation's agent lives in the host process — a choice that did not travel never reached the model that served. There is no automatic model selection: the former smart-selection and measured-mix reselection features were removed (the `IModelSelector` seam, `SmartModelSelector`, `SmartSelectionOptions`, `ModelSelectionResult`, `MeasuredMixPolicy`, `MeasuredMixPrior`, and the `DynamicReselectionCoordinator` were deleted). The persisted `ModelUsed` pin is the record of what actually served — resume stability and the status bar read it — and is re-pinned only when the user picks a model; the fallback id and `AgentRecord.UnassignedModel` count as unpinned. **MODEL SELECTION IS ONE DECISION IN TWO HALVES: the model, and the routing VARIANT** (Standard / Nitro / Floor / Cache Floor).
`ModelVariant` (`ModelVariant.cs`) carries four routing choices on `ModelConfig.Variant`: Standard uses provider-default routing, Nitro and Floor use the documented `:nitro` and `:floor` model suffixes, while Cache Floor has NO suffix and the OpenRouter ACL writes `provider.order` with `allow_fallbacks: true`. `CacheFloorOrder.Slugs` sorts advertised cache-read prices ascending (unknown or negative last), ties on input price then ordinal endpoint slug, capped at eight. If no tagged endpoint advertises a nonnegative cache-read price no provider object is sent. `provider.sort` cannot express cache-read order (the closed enum accepts price/throughput/latency/exacto only); `provider.only` is deliberately unused because stale entries fail the request, while order is a preference and tolerates stale entries.  `ModelVariants.ApplyTo`/`BaseOf`/`FromModelId` are PURE functions so the resolver, the picker, the status line and the persistence codec cannot invent competing spellings: `ApplyTo` is IDEMPOTENT AND REPLACING (it strips any existing suffix first, so switching back to Standard actually removes a `:nitro`, and re-applying cannot produce `model:nitro:nitro`), and only the two DOCUMENTED suffixes are consumed — a real catalog id like `vendor/model:free` carries a PRICING suffix and is never split.
**THE PROVIDER PICKER IS DELETED, and with it the endpoint pin.** `ModelConfig.Provider` is gone and the OpenRouter request body carries no endpoint pin: the retired pin wrote `provider: { only: [...], allow_fallbacks: false }`, narrowing the request to one endpoint, which is exactly the decision the user no longer makes — a variant sorts or prefers the pool rather than restricting it, so a leftover pin would OVERRIDE the chosen tradeoff (a `:floor` request pinned to one expensive endpoint pays that endpoint while the user asked for the cheapest). `PinnedProvider` and its `UnknownPinnedProvider` failure are deleted: because a variant never narrows the pool, a model the catalog lists is servable under all four variants, so there is no vanished-provider state for a turn to fail on. Provider routing (`OpenRouterRequestSettings.Routing`) remains removed; the Cache Floor order is the ACL's sole provider-body routing writer.
**THE STATISTICS SURVIVE THE SIMPLIFICATION — none of them were removed.** Effective pricing and the cache-hit rate are still computed and STORED per call by the usage ledger; what disappeared is the SURFACE that asked the user to compare endpoints on them (`ProviderComparison`, `ProviderEvidenceRow`, `ProviderPresets`, `ProviderRanking`, the four ordering presets, the provider level, and the published/published-performance loaders the picker wired in). The machinery stays because it is what makes the ledger readable: `EffectivePrice` (blended input price at an explicitly-supplied hit rate, cache-WRITE cost as a separate member, D3's 'no verified caching means no discount'), `ProviderRanking` (lexicographic priorities, nulls last in both directions, hard filters separate from ranking), `ProviderPerformance` (`ProviderPerformanceReport`, `BindEndpoints`, median-not-mean), and `UsageCost` are untouched and still tested where they live. Deleting a view is not deleting a measurement.
**THE CATALOG IS KEYED ON THE BASE MODEL, and the suffix is stripped at every lookup.** `IUsagePriceSource.PricesForAsync(modelId, promptTokens, ct)` and `IContextWindowSource.WindowForAsync(modelId, ct)` lost their provider parameter: the catalog serves one row per ROUTABLE ENDPOINT sharing the model id, so the id alone identifies the price table and the window. Both call `ModelVariants.BaseOf` first, because the wire carries `alpha/model:nitro` while the catalog knows `alpha/model` — looking the wire id up would find nothing, failing every turn of a nitro session with `UnknownModelWindow` and silently leaving every call unpriced. **WHICH ENDPOINT ANSWERS** is now decided by rule rather than by a pin: catalog reference prices come from the CHEAPEST endpoint that advertises them (these are estimates, not the served charge; the response's `usage.cost` is the charge), and the window is the WIDEST over the model's endpoints (the budget must fit whichever endpoint actually serves, which is unknowable before the request, and the widest never under-budgets).
**THE PERSISTED CHOICE IS A MODEL + VARIANT PAIR** (`ModelVariantChoice`, key `model_provider_choice:{provider}:{workspaceRoot}` — the key name is unchanged so no migration is needed). Its codec accepts every shape this harness ever wrote: a bare model id and the retired provider-pair JSON both restore the MODEL and leave the variant UNSET (a provider chose under a deleted surface must never be resurrected as a routing decision the user did not make), a legacy id already carrying a suffix is SPLIT into base + variant so the picker preselects the right row, and an UNKNOWN OR NUMERIC variant name is a named `InvalidModelChoice` failure rather than a silent Standard (serving Standard would route a turn the user did not ask for; the shell falls back to its session default, which the user can see). `SessionModelPreferences.ModelVariant` is nullable — null means UNSET, never 'standard was chosen' — and `ModelPreferencesOverlay.ApplyVariant` writes the suffix onto the CONFIG's model and the chosen variant onto `ModelConfig.Variant`, not the preference's model: the session-pin path has a model (the persisted record) while the preference carries only the variant, so gating on the preference's model would silently drop the tradeoff on every resumed session. The variant is inherited by children (a property of the conversation) and applied to each CHILD'S OWN model, and `RootAgentResolver`/`StartSpawnHandler` normalize every id to its base before any catalog lookup.
**THE STATUS LINE NAMES THE VARIANT, and only when one was committed.** `StatusViewModel.ServingVariant` renders nothing for Standard: the default is the absence of a decision, and a bar labelling every session 'Standard' is noise. The Desktop's Model Settings window carries one searchable model list plus a `Routing` dropdown whose four entries are the bare names (Standard / Nitro / Floor / Cache Floor) with the tradeoff stated once in the caption underneath the dropdown — repeating it in every row and in the status bar lengthened the decision without adding to it — and the save's tri-state is on the PAIR — keeping the model and switching the variant is a real choice and reports as Pinned.
**PROVIDER PERFORMANCE IS OBSERVED FROM THE ROWS THE LEDGER ALREADY WRITES (issue #295)**, and remains the honest source: the catalog's own latency and throughput fields are structurally dead (measured live, null on all 52 endpoints across 5 models), so recorded call durations are the only measurement of the provider we actually reached.
`ProviderPerformanceReport.Rankable(entries)` remains the SEAM into ranking (issue #294's `RankableProvider`): measurements arrive as OBSERVATIONS, an unmeasured pair arrives as NULLS rather than zeros, and matching is by the PAIR so one provider's numbers never bind to another model's row. The read is capped (`PerformanceRowCap`, newest rows first) and a capped read SAYS SO (`Truncated`) instead of presenting a partial read as complete history. The usage ledger's READ side lives here too (issue #24): `IUsageQueries` (session rollups over the persisted usage rows), the neutral `UsageRow`/`UsageTotal`/`UsageSummary` shapes, the ONE cost formula (`UsageCost`), and the `UsageTally` accumulator the status bar seeds and advances. **OBSERVED PROVIDER PERFORMANCE (issue #295)** is the second read model over those same rows, and it exists because the catalog cannot answer the question: `ProviderPerformanceAsync(ProviderPerformanceRequest)` returns a `ProviderPerformanceReport` of one `ProviderPerformance` per (model, provider) PAIR — median call duration, p90 duration, median first-token latency, median output rate, and the token counts the hit rate derives from — each with its own SAMPLE COUNT, because a median over three calls is not a median over three thousand (D1). **MEDIAN, NOT MEAN (D2)**: provider latency has a long right tail (a single 578-second call measured in this workspace would move a mean by seconds and describe nothing), pinned by test against exactly that fixture. **A CALL WITH NO OUTPUT IS EXCLUDED FROM THROUGHPUT (D3)**, never clamped to zero — a tool-call-only response has no rate, and letting it through would drag the median toward zero and call a fast provider slow; a zero-duration call is excluded for the same reason rather than reporting an infinite rate. **THE HIT RATE IS AN OUTPUT OF THE SAME QUERY AS THE ROLLUP (D4)**, derived by `UsageStatistics.HitRate` from the counts in scope, so the number the picker multiplies prices by and the number the status bar shows cannot disagree — the structural version of the `UsageCost` precedent. **SCOPE IS A FIXED FALLBACK CHAIN — session, then workspace, then global (D5) — AND THE REPORT NAMES THE RUNG THAT ANSWERED** (`UsageScope`), because a fresh session has no rows of its own and a projection built on an unstated scope is a guess wearing a decimal point; a request naming neither id is a NAMED FAILURE rather than an answer from the whole ledger. **A LEGACY ROW WITH NO `DurationMs` IS EXCLUDED FROM LATENCY AND COUNTED AS UNMEASURED (B6)**, never treated as a zero-duration call. The arithmetic lives in `UsageStatistics` as PURE functions (`Median`, `Percentile` — NEAREST-RANK, so a percentile is a duration some call actually took — `OutputTokensPerSecond`, `HitRate`), and the ACL aggregates in C# over the same rows the summary reads rather than in a second SQL implementation. `ProviderPerformanceReport.Rankable(entries)` is the SEAM INTO RANKING (issue #294's `RankableProvider`): measurements arrive as OBSERVATIONS, an unmeasured pair arrives as NULLS rather than zeros, and matching is by the PAIR so one provider's numbers never bind to another model's row. The read is capped (`PerformanceRowCap`, newest rows first) and a capped read SAYS SO (`Truncated`) instead of presenting a partial read as complete history. Context accounting lives here too: both ACLs report provider-scored `TokenUsage` on every response, `ModelConfig` carries a nullable `ContextWindow` — null means not yet catalog-resolved (bootstrap configs); every serving model's window resolves from the provider catalog through `IContextWindowSource` (no curated constants exist; OpenRouter's `openrouter/auto` is a fetched catalog row at its API-reported size), and a catalog miss fails the turn/spawn loudly (never a fabricated window), and `ContextAccountant` (`IContextMonitor`) keeps utilization against that window — provider usage reports are the only decision input; character-based numbers are estimates for UI breakdowns only. It also accumulates the two provider-scored numbers the reasoning-in-context work (#261) is measured with (#262): the prompt-cache hit count (`input_tokens_details.cached_tokens`) and the reasoning-token count (`output_tokens_details.reasoning_tokens`), both carried on `TokenUsage` and both NULL when the provider omits them — a reported `reasoning_tokens: 0` (reasoning that billed nothing) stays a different fact from no report at all, never coerced to zero — with the cache-hit ratio DERIVED on `ContextStatus` (`CacheHitPercent`) so no caller can hand in a ratio that disagrees with the counts it came from. The catalog's `ModelProviderEntry` carries a NULLABLE `PromptCacheReadPricePerToken` (issue #22) parsed from the endpoints API's `input_cache_read` at both the model and per-endpoint level — nullable because "no cache price advertised" is a different fact from "cache reads are free", and a negative advertised value (the routing pseudo-models' -1, "set at routing time") is not a price at all — and `CatalogUsagePriceSource` (`IUsagePriceSource`) resolves catalog reference prices a usage row stamps, memoized per base model for the process lifetime while a FAILED catalog read is deliberately not memoized (a transient fault must not poison every later stamp with nulls). Both ride the `context` wire payload as defaulted members (an older host's omission reads as unreported) so the CTX line's `, cache 82%, reasoning 1.2K` segments advance in a host-run session, and a provider reporting neither renders exactly the pre-#262 line. Model resolution is deterministic and preference-driven: the user's live model choice (via `SessionModelPreferences`) wins, then the session pin (the persisted `ModelUsed`, the record of what actually served) — and then NOTHING: a session that names no model FAILS the turn (`NoModelSelected`) and a named model whose catalog window is unknown FAILS it too (`UnknownModelWindow`). The harness never substitutes a different model: the user picked `minimax/minimax-m3.1-flash:free` and the turns ran on `openrouter/auto` (2026-10-22) — a silent substitution is a lie about what ran. The Desktop therefore always NAMES the session's model (the user's persisted pick, else the session's pin — the record of what actually served, so a resume continues with it — else the session's default), so the status bar and the model that serves are the same model, and the live choice RIDES the root-turn request (`RootTurnRequest.ModelPreferences`, opaque JSON decoded host-side) because the picker lives in the app while the conversation's agent lives in the host process — a choice that did not travel never reached the model that served. There is no automatic model selection: the former smart-selection and measured-mix reselection features were removed (the `IModelSelector` seam, `SmartModelSelector`, `SmartSelectionOptions`, `ModelSelectionResult`, `MeasuredMixPolicy`, `MeasuredMixPrior`, and the `DynamicReselectionCoordinator` were deleted). The persisted `ModelUsed` pin is the record of what actually served — resume stability and the status bar read it — and is re-pinned only when the user picks a model; the fallback id and `AgentRecord.UnassignedModel` count as unpinned. **THE CACHE-HIT RATE IS STILL RESOLVED FROM EVIDENCE, and the machinery that does it was NOT removed with the picker.** `HitRateAssumption` carries the rate a comparison projects prices at TOGETHER WITH ITS SOURCE (`Session` / `Workspace` / `Global` / `Default` / `Manual`) — the rate is never read without its provenance, because a projection built on an unstated assumption is a guess wearing a decimal point; `Describe()` gives every source its own sentence so a measured rate and an invented one never render alike, and the documented default is mid-range (`DefaultRate = 0.5m`): zero would make every provider look as though caching never helps, and a high figure would project one workspace's behaviour onto every user. `HitRateResolution.Resolve` walks a fixed chain per model+provider PAIR — our own ledger's measured rate for that pair, then the rate the provider PUBLISHES for that endpoint, then the documented default — and `HitRateLookup` is the per-pair carrier, so no row can be priced at a rate it did not resolve. **THE MEASURED RUNG BINDS TO THE ENDPOINT, NOT THE PROVIDER NAME** (measured 2026-10-27): reading the rate by name while the PRICE is keyed per endpoint blended every variant into one figure and INVERTED the ranking — Morph at 98.5% beat DeepInfra flex at 97%, where at one rate on both, flex wins by 5% (crossover 97.91%). `ProviderPerformance.LookupByEndpoint` answers a tagged row, `LookupByName` answers ONLY an endpoint-less row (the legacy shape, whose measurement genuinely describes the name), and an endpoint never called resolves the published rate or the stated default rather than inheriting a sibling's figure. `ProviderPerformanceReport.BindEndpoints(entries)` establishes that identity from the CATALOG and binds ONLY a real variant slug.

**THE CHOICE IS THE MODEL AND ITS ROUTING VARIANT, AND NOTHING ELSE WRITES ROUTING.** The retired provider pair — `SessionModelPreferences.ProviderName`, the `provider: {only:[...], allow_fallbacks:false}` pin, and the `PinnedProvider`/`UnknownPinnedProvider` failure it needed — is DELETED; see the Model Domain's **MODEL SELECTION IS ONE DECISION IN TWO HALVES** passage for what replaced it, why a variant cannot strand a model the way a pin could, and how the persisted `ModelVariantChoice` reads every legacy shape. What survives from the pin era, unchanged and deliberately so, is the ONE-SMOKE-TEST RULE: **`ModelResponse.ServedServiceTier` parses the Responses API's top-level `service_tier`** (default/flex/priority/ultrafast, null when upstream reported none) through `ResponsesApiRequestCore.ParseServiceTier` on BOTH parse paths, because a request states an INTENTION and the response field is the only fact the wire returns about which tier actually served. It is never backfilled from the requested variant or tier — the same rule `ServedProvider` follows — and it is recorded as reported rather than inferred. The reported `usage.cost`, not the requested variant or catalog estimate, supplies the charge. Stored `provider_settings` payloads written before the routing removal are still swept at startup: `DeadPreferenceSweep.DeadMembersByKeyPrefix` strips the dead `routing` member IN PLACE (the row survives — it still carries server_tools/plugins/reasoning_summary) and reports `<key>#routing`; an unparseable payload is left alone and reported, because a cleanup that rewrote corrupt storage would destroy the evidence. There is no configured model pin — model choice is runtime-only. `SessionModelPreferences` carries runtime-adjustable knobs — reasoning effort and model, both via the Model Settings window, plus TWELVE provider-neutral sampling knobs (top-p, top-k, frequency/presence/repetition penalties, min-p, top-a, seed, verbosity, parallel-tool-calls, and the temperature and max-tokens caps) set through the Model Settings window. Every knob is a nullable runtime preference: a null knob is OMITTED from the request body so the provider default applies — true for the ten nullable sampling knobs, while temperature and max-tokens are non-nullable on `ModelConfig` and always travel (a null preference there means the app-resolved default, not an omitted key). The `ModelPreferencesOverlay` overlay carries them onto every resolved config (root and children alike); OpenRouter-only request settings (the ten server tools available on the responses API (openrouter:subagent was removed as an option — its server-side agent loop cannot complete inside the request timeout, and the harness owns subagents natively), plugins, loop budgets) are typed in the OpenRouter ACL (`OpenRouterRequestSettings`) and travel as OPAQUE JSON in `ProviderSettings` — domain code never interprets them —. The effort choice — model default or one of seven levels — maps to OpenRouter's unified `reasoning.effort` and is persisted + restored per workspace + provider. The **Reasoning summary (display)** selector beside it is the parent #261 display channel (#264): a nullable `ReasoningSummaryLevel` (`Auto | Concise | Detailed`) on `OpenRouterRequestSettings`, carried in the same opaque `ProviderSettings` payload and emitted as `reasoning.summary` beside `effort` — the two knobs are INDEPENDENT, so either can be set alone and the `reasoning` object is emitted whenever either is (neither set omits the key entirely). It is display-only by construction: it changes what the provider streams into the transcript and never the request's `input` array (pinned by test on both the ACL and the E2E path), because the harness asks the provider for its own summary rather than writing a summarizer or asking the model to narrate its thinking.
- **Capability Domain**: the registry that merges providers and exposes tools and capabilities to the model.
- **Memory Domain**: recall and search over persisted sessions (lexical and bounded-regex query planning). The former curated-memory learning loop was removed (issue #236); the project keeps only the recall machinery behind the `memory` provider.
- **Skill Domain**: the methodology-skill subsystem — three skill sources under one contract. Embedded built-in skills ship verbatim (`EmbeddedSkillCatalog` over SKILL.md resources in the Skill Domain assembly, including the using-skills session contract and the ethang-tools-mapping tool-binding skill); file skills load from user-configured directories in agentskills.io format (each immediate subdirectory holding a SKILL.md, or a SKILL.md at the directory root, is one skill — everything else in the folder is ignored); learned skills are agent-created, with version history and usage tracking. The `CompositeSkillCatalog` merges built-ins and file skills with precedence built-in > global-directory > workspace-directory — a file skill never shadows a built-in, and later same-name entries are shadowed with a `[collision]` diagnostic — while learned resolution falls through to the store only after a catalog miss. Frontmatter parsing (`SkillMarkdown`) demands `name` and a non-empty `description`; the honored agentskills.io keys are `metadata.version` (integer) and `disable-model-invocation` (a manual skill); known-but-unapplied keys (`allowed-tools`, `license`, `compatibility`) and unknown keys load with per-file warnings — warnings never fail a load, and one bad file degrades to a diagnostic, never a whole-load failure. Manual skills never appear in the always-on listing, carry a `[manual]` marker in `skill_list`, and load by name. Skill directories are host configuration: the `skill_directories:global` / `skill_directories:ws:{root}` preference keys (the same `{path, enabled}` JSON shape as the session-file lists), edited in the Desktop's Open Workspace dialog (moved out of the Settings window); nothing configured means no file skills. Every session (root, children, and remote — the ChildHost resolves the same directories from the settings it serializes via `AgentComposition.ResolveSkillDirectoriesFromSettings`) carries the `SkillsListingPromptProvider`'s budgeted listing: 8,000 characters total, descriptions capped at `SkillListingBudget.DescriptionLimit` (200 — deliberately above the longest real description, so the ANNOUNCED budget pass does the cutting; a 60-character cap was silently amputating the `Use when ...` trigger clause off every skill), grouped Built-in / Global directory skills / Workspace directory skills / Learned, `[collision]`/`[warning]` lines rendered, and a truncation marker whenever any description or entry was dropped — never silent. The session bootstrap (`SkillsBootstrapPromptProvider`) injects the using-skills contract verbatim — prefer a matching skill over improvising, announce it, load its body with `skill_view`, the user's instructions outrank skills — with no emphasis wrapper; the development-methodology skills are description-triggered from the listing, not session defaults. **`reviewing-plans` is the reviewer's rubric (issue #217)**: a chain step assigned the review role is told to load it and apply its three-dimension rubric, and the skill's published verdict tokens are pinned against `PlanReviewVerdictCodec.Tokens` in the composition tests, so a conforming reviewer's verdict always parses into the review record. The tools: `skill_list` (builtin/file/learned source labels, the `[manual]` marker, catalog diagnostics), `skill_view` (the origin directory in the annotation for file skills; usage rows recorded for learned views only), `skill_manage` (refuses to create a name held by a built-in or file skill — `NameCollision` — and reports `BuiltInImmutable`/`SkillNotFound` on update or delete of either); the skill registry tools (`skill_search`, `skill_registry` install/update/uninstall with a deterministic BLOCK/advisory content scan and the `skill_registry:default_target` preference) install community skills into configured directories, surfacing same-session through hot reload — which is live in the container that actually serves the model: `AgentComposition.StartSkillHotReload` is called at BOTH container build sites (`AgentSessionFactory.BuildContainer` and `SessionHost.Create`), because production turns run in the ChildHost process and an app-side-only start left every real session's watcher inert, so a skill added mid-session stayed invisible for the session's whole lifetime (issue #269). The reload announcement reaches the transcript through the container's `SessionNoticeSink` carrier — the sink the shell binds at attach — never through a DI-resolved `AgentSession`, which is registered in no container. Deterministic user invocation (spec #28, superseding skill-routing spec #19 decision 6's gated user-invocation channel) runs through ONE application core: `SkillInvocationService` resolves a name case-insensitively over the full visible+manual catalog (0 hits -> `SkillNotFound`, >1 -> `AmbiguousSkill` listing the matches) and renders the verbatim `[skill invoked: <name>]` System line — description truncated at the 60-character budget, body inlined, a >4,000-character body falls back to a `skill_view` pointer (`SkipReason=oversize`), arguments ride a final `arguments:` line, and NO `skill_usage` row is written (view-hygiene rule). The channels: the `skill_invoke` tool (returns the one-line confirmation, never the body) and the Desktop's `/` slash input — a raw-first-character `/` (no trim) opens the `SkillAutocompleteViewModel` popup (manual skills first, case-insensitive substring filter over the name token, wrap-around navigation, Tab/Enter accept autofills `/<full name> `); at submit, a found name injects the System line then forwards the full input as the ordinary user message, an unknown name stays a plain message, and an ambiguous name sends nothing and surfaces a transcript notice listing the matches. A headless activation eval (`tools/SkillActivationEval` — `ETHANG_EVAL_KEY`, `ETHANG_EVAL_PROMPT_BUDGET_SECONDS`, `ETHANG_EVAL_LOCAL_BASE_URL`; deliberately not part of the solution) drives real sessions over `prompts.json` to measure skill activation, with before/after results captured as plan records.
- **State Domain**: durable, workspace-scoped key-value state, evidence-carrying transitions, and state events.
- **Plan Domain**: durable plan records — ids tied to owning sessions, ordered steps — persisted through the Storage ACL (`plans`/`plan_steps`, migrations V13, V20, V21 and V24). **The todo list is RETIRED (issue #310).** A workspace held 80,726 characters of todo JSON rewritten whole on every change — a fourth competing notion of 'what is being worked on' beside plan steps, chain steps, and the experiment ledger, and the reason no surface could answer that question without reading all of them. `TodoTool`, `TodoDocument`, `TodoInput`, `ITodoListStore`, `StateServiceTodoListStore`, `StateServicePlanTodoCleaner`, `IPlanTodoCleaner`, and `PlanSetStatusResult` are deleted; `PlanStep.TodoId` and the `todo_id` column are gone (V24 rebuilds `plan_steps` carrying the status CHECK forward verbatim, since a column that can only ever be null is a permanent reminder of a deleted concept); the `todo` state namespace's RESERVATION is deleted with it (the service's `current` reservation is untouched, and a stale `todo/list` row is now an ORDINARY key); and `plan.set-status` no longer appends a `cleaned N linked todo(s)` line. **The removal is ANNOUNCED, not silent (D5)**: `DeadPreferenceSweep.DeadStateNamespaces` sweeps the `todo` namespace at app startup and reports each row as `state:<ns>/<name>`, because a workspace whose todos vanish must not look like data loss — the sweep is a STATE sweep, not a preference one, and its namespace match is EQUALITY so a `todos` sibling survives. The Desktop's Plans view lost its todo list, not its plan list: `TodoRowViewModel`, `Todos`, `LoadTodosAsync`, the `todo/list` state-bus branch, and the XAML list are gone and `IsEmpty` is a question about plans alone, so #312 has something smaller to extend rather than something broken to repair. Plan records are persisted through the Storage ACL (`plans`/`plan_steps`, migrations V13, V20, V21 and V24) and exposed through the `plan` capability provider; the experiment-driven-development workflow's design specs and implementation plans are plan records. **The plan REVIEW record is a first-class row (issue #216).** `plan_reviews` (migration V27) persists which plan, WHICH VERSION it judged, the verdict, the three rubric scores, the cited findings, the reviewer's session id and model, and when — and `IPlanReviewStore`/`SqlitePlanReviewStore` is its port, registered beside the plan store because a review is a fact about a plan version and the two share one workspace binding. **THE ROW IS KEYED ON PLAN ID PLUS THE JUDGED VERSION (D1)**: a verdict about version 3 must stay distinguishable from a verdict about version 7 after the planner revises, or a stale approve silently covers content nobody reviewed; the plan already carries its version, so the key needs no new state on the aggregate. **THE VERDICT IS ITS OWN TYPE, NOT A STATUS (D2)**: `PlanReviewVerdict` is exactly `Approve | Deny | ApproveWithConditions`, and `PlanStatus` keeps its three members and its transition rule untouched — an approval is a fact ABOUT the plan, not a state OF it, and folding it into the status enum would change the lifecycle semantics the record exists to observe. **THE STORED TOKENS ARE THE BRIEF'S TOKENS**: `PlanReviewVerdictCodec` encodes to `approve` / `deny` / `approve-with-conditions` — the exact spellings #306's review brief tells a reviewer to write — and decodes STRICTLY, so an unknown value is a named `UnknownVerdict` quoting what it saw rather than a silent default to approve (the safe direction for a gate is 'not a verdict', never 'probably fine'). That deliberately departs from `ChainStepRole`'s member-name encoding: there the harness writes the value, here a MODEL following the brief does, and a second spelling would be a second thing to keep in sync. **THE SCORES ARE THREE NAMED DIMENSIONS (D3)** — requirement coverage, testability, blast radius — because named dimensions are what a rubric-scored judge is for: they compare across reviews and trend, which free text cannot; only NON-NEGATIVITY is enforced here, since the scale belongs to the `reviewing-plans` rubric (#217) and pinning it in the schema would make the record the authority on a rule it does not own. **A FINDING WITHOUT A CITATION IS REJECTED AT WRITE TIME (D4)**: `PlanReviewFinding` requires both text and a citation (a requirement id or a step position), `PlanReview.Validate()` is the single gate and `SqlitePlanReviewStore.CreateAsync` calls it BEFORE the insert, so a record assembled by hand is checked exactly as one built through the factory — the refusal names the offending finding's INDEX, so a caller with twelve findings is not told only that 'something' was uncited. **VALIDATION IS A METHOD, NOT A CONSTRUCTOR**: the store rehydrates from a row it already trusts, so construction must not be able to fail while a WRITE must. **THE REVIEWER IS A SESSION, NOT AN AGENT (D6)**, with its resolved model recorded beside it — a verdict's provenance is part of the verdict, and the same session can be resumed on a different model. **ONE PORT, TWO READERS (D7)**: the chain cursor (#320) deciding whether to advance and the telemetry report (#309) computing calibration read the same rows through `IPlanReviewStore`, so a reported number and an advance decision cannot disagree. **WORKSPACE ISOLATION IS BY OWNERSHIP, NOT BY A COLUMN**: `plan_reviews` carries no `workspace_id` — a review is a child of a plan and the plan already carries the workspace — so every read JOINs through `plans` and a review of another workspace's plan is invisible (a `Create` on one fails `PlanNotFound`, and the foreign key refuses a review of a plan that does not exist at all). The table is APPEND-ONLY (no update, no delete: a review is a historical fact), its `verdict` column is CHECK-constrained to the three tokens so a DIRECT writer — an exec script's SQL — cannot smuggle an out-of-enum verdict past the domain's validation, and its three score columns carry a non-negative CHECK for the same reason. **Completion demands a consistent plan (issue #271).** `PlanStatusTransition` — the Specification the aggregate already evaluates in `Plan.SetStatus` — refuses `Active -> Completed` while any step is `Pending` or `InProgress`, so `plan.set-status Completed` fails with `Error [InvalidTransition]` NAMING the offending positions and statuses (the model acts on it without a `plan.show` round trip) and the stored status is unchanged. Before this the only invariant was 'only an Active plan may go terminal', so completion succeeded on a plan whose steps were all still `Pending` — 22 of 45 completed plans carried zero done steps, and 42.7% of steps inside `Completed` plans were still `Pending`, which is the stale-data mechanism #268 measured. `Abandoned` is deliberately UNAFFECTED: dropping a half-finished plan is the honest exit and refusing it would leave no truthful way out. **Completion also demands a FRESH passing gate (issue #283).** The workspace's own `goal/check` commands must have passed SINCE the newest workspace change — fresh means 'run since the last change', not 'was run once', because a green run from an hour ago followed by five edits proves nothing about the code being declared finished. The check is `CompletionGate` (Tool Domain) over the `IPlanCompletionGate` port the Plan Domain asks through, wired at the composition root by `StateServicePlanCompletionGate`; a refusal is the typed `CompletionGateNotFresh` naming the remedy (`run state.checkgoal`) and the exit (`set the plan Abandoned`), and it runs BEFORE the transition so a refusal leaves the stored status untouched. The harness knows nothing about linters: it never parses `.editorconfig`, never learns a command's language, and ships no built-in command set — it compares two facts the PROJECT supplied. **An unset `goal/check` never blocks** (the check is simply unavailable), and an unverifiable freshness (unreadable tree, truncated walk, a record predating digest tracking) does NOT block either — refusing there would trap the user with no exit, since re-running the gate cannot fix an unreadable tree. `git_commit` is the ADVISORY attach point by contrast: it appends `[warning] ...` and still commits, because committing work in progress is legitimate and a hard refusal there pushes toward `--no-verify`. `state.checkgoal` runs the commands as SHELL COMMAND LINES through `IGoalCommandRunner` (the evidence runner compiles C# boolean expressions and could never have run `dotnet build` — measured 2026-10-25: storing `["dotnet --version"]` reported "The name 'dotnet' does not exist in the current context"), and records the outcome with the workspace digest at `goal/lastcheck`. `PlanStepStatus` gained a fourth member, `Skipped` — the load-bearing half of the design, not a nicety: without a truthful way to say 'not doing this' the cheapest way past the refusal would be to mark unfinished work `Done`, reproducing exactly the false records the gate exists to eliminate. `update-step` accepts `Skipped` and migration V21 widens the `plan_steps` status CHECK to admit it (V20 had pinned the column to three values; the constraint is REBUILT rather than dropped, so the door V20 closed against a direct writer smuggling an out-of-enum value stays closed, and rows/ids/versions are copied verbatim). The workbench's step marker distinguishes the two states — `Skipped` renders a dash and counts as settled, never the `Pending` circle — because a view that drew 'deliberately not doing this' and 'not started yet' alike would undo the distinction the invariant depends on. **A corrupt row is contained to its own plan (issue #279).** `ListAsync` returns a `PlanCatalog` — the readable plans plus a `CorruptPlanRow(PlanId, Reason)` per row that could not be materialized — so one unreadable row can never blank the workspace catalog; `GetAsync` fails that one plan with the named `CorruptPlanRow` code instead of throwing; `plan.index` renders each corrupt plan on its own `#<id> [ CorruptPlanRow ] <reason>` line after the healthy ones. Status parsing requires a DEFINED enum member (`Enum.TryParse` alone accepts `"5"` and yields an out-of-range value, which would smuggle it into the domain). Migration V20 repaired the six `plan_steps` rows that carried `Completed` (a `PlanStatus` value in a step-status column) to `Done` — any other unknown step status becomes `Pending`, never a guessed completion — and added CHECK constraints to `plans` and `plan_steps`, so a DIRECT writer (an exec script's SQL) can no longer reintroduce the corruption; the tables are rebuilt with foreign-key enforcement suspended around the swap and ids/versions preserved verbatim.

## Project Structure

The solution follows a layered DDD structure. Each bounded context has its own project with:

- `Domain` — aggregates, entities, value objects, domain events, specifications, repository interfaces
- `Application` — commands, queries, handlers, application services
- `Infrastructure` — repository implementations, ACL implementations, external service adapters
- `Contracts` — public interfaces, DTOs, and contracts shared across boundaries (kept minimal)

Shared kernel (cross-cutting concerns shared across domains):

- `SharedKernel` — base types, common value objects, guard clauses, result types

ACLs live in an `ACL` project each, implementing domain-owned interfaces.

### Naming Conventions

- Domain namespaces omit the dot: `eThangAgent.ToolDomain`, `eThangAgent.ConversationDomain`.
- ACL namespaces keep it: `eThangAgent.OpenRouter.ACL`, `eThangAgent.FileSystem.ACL`.

## Development Conventions

- **No shell intermediary**: repo automation is plain `dotnet` CLI invocations; do not commit `.ps1`/`.sh`/`.cmd`/`.bat` scripts. If a task needs scripting, prefer C# (the same language as the codebase).

- **Build**: `dotnet build`.
- **Formatting & analyzer severity**: enforced mechanically — `.editorconfig`, `Directory.Build.props`, and the CI lint job are the source of truth; this document deliberately does not restate their rules. Apply with `dotnet format whitespace eThangAgent.slnx` before committing (apply analyzer fixes only per rule, never in bulk — `dotnet format` without a subcommand also applies semantic analyzer fixes and can rewrite signatures), then verify with the exact CI lint gate before pushing: `dotnet format eThangAgent.slnx --verify-no-changes --severity warn`. That verify command is a strict superset of the whitespace subcommand — it also runs style and third-party analyzers (the JSON001–005 family, e.g. `Probable JSON string detected`), which never surface on `dotnet build` even with `EnforceCodeStyleInBuild` + `TreatWarningsAsErrors`, because the family executes only in the format/IDE host and not the batch compiler; the verify run is their only automated net. (The signature-rewrite hazard is apply-direction only — `--verify-no-changes` writes nothing.) Sonar rules (SXXXX) are enforced at build time via `SonarAnalyzer.CSharp` (referenced in `Directory.Build.props`), mirroring the SonarQube Cloud profile: a finding must surface on `dotnet build`, not only after push. xUnit rules (xUXXX) are enforced at build time via `xunit.analyzers` (pinned in `tests/Directory.Build.props`; xunit.v3 3.2.x already pulls ≥ 1.27.0 transitively, so the pin exists to take 2.0.0's rule set ahead of the xunit.v3 4.x bump, which requires ≥ 2.0.0 and therefore conflicts with nothing). Named deviations live in `.editorconfig` (S1135, S125 off — their heuristics collide with this repo's prose) or targeted `#pragma warning` pairs at by-design sites (deliberate empty base records, provider base-URL constants, best-effort cleanup catches). Two carve-outs are named decisions, not leniency: CA1707 (xUnit `Method_Scenario_Expected` names) is suppressed in test projects only; CA2007 (`ConfigureAwait`) is suppressed in `eThangAgent.Desktop` only, because the UI SynchronizationContext is load-bearing — view-model continuations must resume on the UI thread. In test projects, awaits of same-assembly tasks use `ConfigureAwait(true)` in xUnit test methods and `ConfigureAwait(false)` in fake/helper classes (xUnit1030 forbids `false` in test methods).
- **Testing**: xUnit. Three layers: unit, integration, and E2E tests. Solution-level `dotnet test eThangAgent.slnx` runs every test project concurrently (Microsoft.Testing.Platform: one testhost per project, up to `Environment.ProcessorCount` modules at once); on a loaded machine the timing-sensitive integration tests (named pipes, git worktrees, Roslyn shell kills) can contend — pass `--max-parallel-test-modules <n>` (e.g. 4) to bound the concurrency. There is NO desktop-driving computer-use test suite: the owned-window integration tests were removed deliberately (they popped real windows and raced the user's own desktop use); computer-use coverage is stub-host supervision tests, wire/contract tests, and the fake-access E2E — nothing creates windows or injects input on the user's desktop. Aim for 100% coverage; minimum 80% required. Unit tests use fakes only — a domain test must never know PowerShell, HTTP, or OpenRouter exist. Integration tests exercise real ACL implementations against real files / sandbox endpoints. E2E tests drive the desktop app headless — real composition behind the view-model — against a local mock provider server. Test selection runs on the xunit.v3 / Microsoft.Testing.Platform runner, not VSTest: `dotnet test --filter` is rejected (exit 5, help dump) — use `--filter-class` (fully-qualified class name), `--filter-method`, `--filter-trait`, or `--filter-query`; the runner also rejects `--no-build` and `--nologo` (exit 5, help dump) — plain `dotnet test <project> --filter-class <FQN>` is the working form; exit 2 means failures, exit 8 means zero tests matched.

- **Session retrospective**: at the end of every session/task, evaluate how *the agent itself* handled the session — bugs in its behavior, gaps in its tool surface, missing skills or workflow support — and include that evaluation in the summary to the user rather than letting it evaporate. The retrospective evaluates and targets the harness itself — a general agent that can be used on any repository, in any language, for multiple users — never the host repo: suggestions must target the agent (new tools, capabilities, prompts, reliability), never one-off fixes baked into a specific repo. A pattern that recurs across sessions or repos is a signal to promote it into a first-class agent capability. It also places the session AGAINST the constitution this document opens with: how the work done and the agent's own conduct moved the project toward the [Overall Goal](#overall-goal), honored or strained the [Guiding Philosophy](#guiding-philosophy), and followed or bypassed the [Architecture Principles](#architecture-principles) — and where the change drifted, naming the concrete site (a seam bypassed for an implementation detail, a mechanic left to the model where a tool or gate belongs, state written to an ad-hoc file where an owned store belongs, a comment that promises what the code does not do). Restating a principle is not a finding; a principle with nothing to say this session gets one line saying so. The retrospective also reports the session's loop telemetry in one fixed line — hypotheses stated, predictions tested, refuted count, skips recorded — read from the plan's `sci.<slug>/ledger` through the `experiment` tool; the records ARE the telemetry, so there is no second store.
- **Deadlock vigilance in tests**: a test that can wait forever eventually will. Any test exercising an unbounded or externally-settled await (channels, gates, `TaskCompletionSource`) must have a reachable completion path under the code under test's *current* contract — before running the suite, trace what settles the await. When a contract changes from bounded to unbounded, update every test that relied on the old bound in the same change, asserting the new contract directly rather than scripting the old one. A hung test blocks the whole suite and the agent itself; after fixing the cause, kill the orphaned `testhost` process before rerunning.
- **Every change leaves the build green**: a task is not done if the solution does not build and all tests pass.
- **Green includes a clean tree**: a task is not done while `git status --porcelain` shows output. Intended changes are committed; unintended ones are reverted or surfaced. Uncommitted work is unfinished work.
- **Dependency injection**: all wiring at the composition root — the host-agnostic `eThangAgent.Composition` library (`AgentComposition`/`AgentSessionFactory`), consumed by the Desktop host. Domains depend only on interfaces and contain zero DI container references.
- **Immutability**: domain models prefer immutability — records, init-only properties, copy constructors.
- **Error handling**: result types, not exceptions, for expected domain failures. Exceptions are for infrastructure/programmer errors.
- **Tool design**: tools demand strictly correct input (see Guiding Philosophy). Tool errors are returned to the model as tool results — an error is feedback for self-correction, never a turn-ending crash. The loop's `ToolRepeatGuard` guards three loop shapes — two failure-fed and one success-fed. Identical-args nudges at the 2nd/5th identical failure, plus a cross-argument breaker that counts consecutive failures of one tool across ANY arguments, nudges at the 3rd and SUSPENDS the tool at the 13th (3+10) — the loop then refuses further calls with `Error [ToolSuspended]` without executing them (2026-10-04: ~200 varied failed exec calls never re-tripped the identical-args nudges). The success-repetition breaker (2026-10-08: a depth-1 subagent re-ran one identical exec call 235 times over 2.5 hours, every call returning the same 2843-char payload — invisible to a guard fed only by `isError`) counts consecutive byte-identical SUCCESSFUL calls of one tool, nudges at the 3rd and SUSPENDS at the 13th, mirroring the failure breaker; a failure, a different tool, or different arguments resets it, so legitimate polling is not punished. The loop keys both identical-args streaks on the tool's SEMANTIC call identity, not raw arguments (issue #124, 2026-10-15: the model varied exec's `title` envelope field every call, resetting the streaks 195 times over one identical call) — a tool declaring `IToolCallIdentifiable` (exec: the program body) feeds its identity to the guard; envelope fields the model free-varies (`title`, `timeoutSeconds`) can no longer reset a streak. Model-facing output uses explicit format contracts (annotation lines, gutters) documented verbatim in the tool description, so the model never has to guess what it is looking at.
- **Performance**: hot paths (file reads, shell execution) go through in-process hosting where possible; avoid per-call process spawns. Streaming over loading: read only the requested range, then account for the whole. Aim for event-driven flow over polling loops, and keep steady-state memory small — don't hold what you're not using. Maintain high performance, low latency, low memory, and a modular event-driven architecture across every change.
- **`edit` is the patch surface**: a multi-place change to one file is ONE `edit` call with `hunks` — a JSON array of `{old, replacement, all|occurrences}` applied atomically over one file read, all or nothing, with one annotation line per hunk — never N sequential anchor calls (which race each other and invalidate line numbers) and never a whole-file rewrite (issue #252). A partial patch cannot exist: any hunk failing to match applies nothing and the error names the hunk and why. A new patch-like tool must not be created; `edit` absorbs what keeps models out of hand-rolled rewrite scripts.

- **Create tools as you work**: when something useful is missing, add a tool for it rather than working around the gap. Tools are the agent's first-class surface — a missing capability is a missing tool, not a one-off script. New tools follow the existing `ITool` / capability-provider contracts: strict input validation, `Result<T>` errors, and verbatim format contracts in the description.
- **Prefer tools over exec scripts**: the Roslyn `exec` engine is for one-off glue, not a substitute for first-class capabilities. When the model keeps writing the same or similar scripts across sessions — repeated file probing, shell-out patterns, query shapes — that is a signal to promote the pattern into a general tool with proper validation and format contracts. The model should spend its effort on decisions, not on re-deriving boilerplate C#.
