## What This Project Is

eThang Agent is an AI agent harness built with .NET, delivered through an Avalonia desktop application. The project follows strict Domain-Driven Design: layered bounded contexts, Specification patterns, and CQRS.

> **Read [`README.md`](README.md) first** — it carries the high-level overview and usage instructions. Whenever a change makes either stale, update the README in the same change.

## Guiding Philosophy

These principles explain every convention below. When a rule seems arbitrary, it traces back to one of these.

- **Seams over commitments.** Every external dependency — AI provider, shell, file system, UI — sits behind an interface the domain owns. Nothing external is ever allowed to become load-bearing inside a domain. Any implementation behind a seam must be replaceable without touching domain code.
- **Strict correctness at the boundaries.** Inputs crossing into the domain are validated completely: required parameters are required, types are exact, unknown input is rejected, and nothing is silently coerced, defaulted, or clamped. Deliberate exceptions exist but are named, documented decisions, never defaults — each proves the rule: (1) a benign overshoot that is clamped with a visible warning; (2) a nested exec-script tool call that omits timeoutSeconds inherits the enclosing exec call’s budget (restating the budget per nested call cost real sessions repeated failures; explicit nested values still win and are still validated; the inherited budget is INJECTED only into actions whose contract declares timeoutSeconds, and STRIPPED from the rest — so every ITool-backed action must declare the parameter, guarded by a composition-level invariant test — and an exec run that completes with empty output while nested calls ran is annotated with a discarded-result hint; a program that references Directory.GetCurrentDirectory() carries a workspace-note annotation stating the launch directory and the workspace root, because the two differ and scripts that confuse them silently read the wrong directory).
- **Errors are information, not crashes.** Expected failures flow through `Result<T>` / error values and are delivered to whoever can act on them — including the model itself, which receives tool errors as tool results so it can self-correct. Exceptions are reserved for programmer error.
- **Reversibility by construction.** The architecture must not preclude alternative frontends, platforms, providers, storage engines, or orchestration topologies. When a choice would foreclose an option, choose the seam instead.
- **The codebase is not the standard.** Existing code records what was done, not what is right. Never treat a current pattern as best practice just because it is present — when work touches code and a better way exists, improve it in the same change. Improve what you touch; do not launch unrelated refactors.
- **Lean, event-driven operations.** Aim for high performance and a small memory footprint. Prefer event-driven designs — react to what happened instead of polling, stream instead of loading, and don't hold what you're not using.
- **Direction: a self-contained agent.** The long-range shape (per the grand plan's philosophy, not its plan details) is a persistent desktop application that manages its own world — conversations, sessions, state, configuration — in app-owned structured storage rather than scattered project-level files. Work written today must fit that destination: durable state flows through domain-owned stores, never ad-hoc files.

## Architecture Principles

### Domain-Driven Design

The codebase is organized around business domains, not technical concerns. Each domain owns its models, logic, and boundaries. Domains communicate through well-defined contracts — never by reaching into another domain's internals.

- **Ubiquitous Language**: domain models and code reflect the language of the problem space (agents, conversations, tools, providers).
- **Bounded Contexts**: each domain has clear boundaries and single ownership of its concerns.
- **Aggregates**: consistency boundaries are enforced through aggregate roots.
- **Domain Events**: side effects across domains are communicated through events, not direct calls.

### CQRS (Command Query Responsibility Segregation)

Commands and queries are separated:

- **Commands** mutate state and do not return data. They go through domain logic, validation, and specification evaluation.
- **Queries** return data and have no side effects. They bypass domain logic and use optimized read models where beneficial.

### Specification Pattern

Business rules and validation logic are encapsulated in composable Specification objects. Specifications can be combined (and, or, not) and are evaluated against domain objects before mutations are applied.

### Anti-Corruption Layers (ACLs)

Any external system or platform-specific concern is isolated behind an Anti-Corruption Layer. The domain never depends directly on external SDKs, platform APIs, or infrastructure. ACLs translate between the domain's ubiquitous language and the external system's concepts. An ACL exists because its seam earns its keep — each table row states why the seam exists.

**Root turns over the transport.** Two envelope kinds ride the same
framing and pumps as the child-run kinds: `root-turn` (app → host: `RootTurnRequest` =
turn id + input + seed) and `root-turn-event` (host → app: `RootTurnEvent` = turn id +
kind + payload + generation). The event kinds are a STRICT set — `delta`, `reasoning`,
`notice`, `tool`, `settled`, `progress`, `session-request`, and `context`; an unknown kind
is a protocol error, never a forward-compatible unknown. `context` carries the loop's
`OnContextUpdate` snapshot (`RootTurnContextPayload`: last input tokens, session totals,
catalog window, utilization, and the estimated bucket breakdown) so the status bar's CTX
line advances for a HOST-run turn exactly as it did in-process — the accountant lives in
the host, so a snapshot that did not travel left every production session's CTX frozen
(issue #255). A `tool` result payload is a JSON object carrying the tool's name, status, rich title, summary, FULL content, and its IMAGES (`RootTurnToolResultPayload.Images`, issue #230 — every conversation runs in a host process, so an image that does not ride this payload can never be rendered; absent means empty, so an older host's payload still parses). `RootTurnProtocol` is the codec; `RemoteAgentRuntime
.SendRootTurnAsync` is the app-side call and `ChildHostServer` the host-side case. The host
**must echo the request's generation verbatim** — the app drops any event whose
(id, generation) does not match the live turn, which is what keeps a reused turn id safe.
Turns are bounded by `RootTurnBudget` (idle bound that resets on every event, a separate
hard ceiling, and a separate generous SEND bound — never the idle window, because a lapsed
write is cancelled and a mid-frame cancellation is unrecoverable). The idle bound measures
LIVENESS, not busyness: the host HEARTBEATS (a `progress` event) whenever a turn has been
quiet, because a long tool call (an exec script, a subagent wait) emits nothing at all —
the app used to read that silence as a dead host, fail a HEALTHY turn, and abandon it while
the host kept running it, and that abandoned turn held the host's turn gate, so every
later turn queued behind it and failed the same way (the session was unusable from the
first error onward, 2026-10-22). The heartbeat interval is a quarter of the window the app
enforces, and the window rides the request (`RootTurnRequest.IdleTimeout`) so the two can
never disagree. An ABANDONED turn is also RELEASED: the app tells the host to stop the
turn it is no longer waiting for (`InterruptRootTurn`), so the gate is freed and the next
turn runs. A bounded send is
CANCELLED rather than abandoned, so the write gate is released; and because the frame header
and payload are two stream writes, a cancellation that interrupts a frame leaves the peer's
frame stream permanently desynchronized — `TransportFraming.WriteAsync` reports that as
`TransportFrameInterruptedException`, and the runtime answers it with `MarkConnectionLost`,
tearing the connection down and completing every pending root-turn waiter and child settle
with a declared failure instead of leaving a silently dead connection that still reports
itself alive. Configuration: the single preference key `subagent_root_turn_idle` (a
constant-format duration) → `SubAgentConfiguration.Bind` → `SubAgentOptions.RootTurnBudget`.
There is deliberately NO total-duration ceiling (issue #248): a wall-clock cap on a whole turn
killed legitimate long work — big investigations, long test runs, waiting on subagents — with
nothing to resume, so the idle window (liveness, reset by every event and by the host's
heartbeat) and the send bound (one frame on the wire) are the only two bounds, and a turn runs
until the host settles it or the caller stops it. `TurnCeilingExceeded` no longer exists. The
host RUNS the
turn (`RootRunHost`: the container's own `SendMessageCommandHandler`, so the conversation the
model reads is the host's), and it answers a turn it cannot run with a typed settle that
NAMES THE REAL CAUSE — "not bound to a root session (the host settings named no root
session id)" for a missing binding, "(<reason>)" for a container that could not be built.
The previous build swallowed that exception and reported the binding instead, so a locked
database read as a wiring fault (2026-10-22). A host whose deployment is incomplete (its
dependency manifest missing — a publishing app copies a referenced project's assemblies
but not its `deps.json`) says so at the same place, with the root cause under it
("DllNotFoundException: Unable to load DLL 'e_sqlite3'").

**Starting a new session is a REQUEST the app answers, and the tab is replaced IN PLACE
(issue #234).** Two more kinds ride the same framing: `session-request` (host → app, a
`RootTurnEvent` whose payload is `SessionRequestPayload` = request id + prompt + optional
handoff summary) and `session-response` (app → host, `SessionResponseCommand` = request id +
session id OR error code/message). `NewSessionRequestChannel` (Composition) carries the live
turn's emitter and the pending requests' completion sources: `RootRunHost` connects it at
turn start and disconnects in the turn's `finally` (pending requests then fail
`SessionRequestUnreachable` — the turn that could carry the answer is gone), and
`ChildHostServer` routes the app's response back through `CompleteSessionRequest`. The
channel is per-turn on purpose: a request emitted with no live turn fails immediately
instead of hanging.

The rule the whole feature exists to honor: **starting a new session NEVER opens a new
tab.** `MainViewModel.StartNewSessionAsync` (the user's `/new`) refuses while a turn runs
(`TurnBusy` — replacing the session would dispose the container under the running turn),
creates, and swaps the tab at the SAME index, firing the prompt as the new session's first
turn; the old session is completed gracefully first, so the Sessions dialog can still resume
it, and its container is disposed (which kills its host process).
`MainViewModel.HandleSessionRequestAsync` (the tool/handoff path) ANSWERS FIRST — the host
is blocked — and only then swaps, waiting for the requesting turn to go idle because the
host emits the request from inside its own turn. Every refusal path answers with its typed
code (`TabClosed`, `SessionRequestPending`, `SessionLaunchFailed`, `SeedUnsupported`); an
unanswered request is a tool waiting out its whole budget for an answer that was never
coming, and a second request while one is pending is refused rather than queued (two
launches racing for one tab slot would leave one session alive in no tab at all). A tab that
closes during the wait disposes the session it asked for instead of leaking it.

The compaction handoff (`compaction_handoff_enabled`, default OFF) rides the same channel:
`DefaultContextCompactor` returns a `CompactionOutcome.Handoff` instead of compacting in
place, the loop ends the turn with the named handoff line, and `RootRunHost` emits the
request with an EMPTY prompt (seed-only — a handoff continues from the summary, it does not
re-ask) and the summary. `SessionHandoffSeed` owns the seed shape: a System message flagged
`IsSummary` (the shape every surface already understands) under a prefix that says the
session CONTINUES from an earlier conversation rather than claiming a compaction that never
happened, and the factory persists the seed rows explicitly (the transcript sink's baseline
counts the seeded prefix as already-persisted, so without that a resume would lose it). A
blank summary seeds nothing, and a host with no seeded creator refuses the handoff
(`SeedUnsupported`) instead of silently dropping the summary it exists to carry.

A special seam sits beside the ACLs: `eThangAgent.Provider.Wire`, the shared Responses-API wire core (request `input`-item building, flat function-tool translation, non-streaming `output` parsing, and typed-event SSE stream application) consumed by the provider ACL. It exists because that logic is OpenAI Responses-wire plumbing while living entirely outside the domain. The doctrine this refines: ACLs share no **domain** code; provider wire plumbing may live in a shared infrastructure project.

## Technology Stack & Constraints

- **Runtime**: .NET 10
- **Language**: C#
- **Platform**: Windows only — all path handling, process execution, and scripting assume Windows.
- **Exec / Scripting**: Roslyn C# scripting via the Exec ACL (`IExecEngine`) — no PowerShell anywhere in the solution. External processes (e.g., `git`) are spawned directly with native .NET `Process` APIs.
- **AI Providers**: OpenRouter — the domain model speaks in provider-neutral concepts, and each provider's ACL implements them. Sessions are wired exclusively for one provider; switching providers is a different experience by design.
- **Interface**: Desktop (Avalonia)

### Packaging & Wiring

- Each domain and ACL is its own project (package) for composability.
- Packages are designed to be swapped or extended — replacing an ACL implementation must never require touching domain code.
- Dependency injection wires implementations at the composition root; domains depend only on interfaces and contain zero DI container references.
- `eThangAgent.ComputerUse.Host` is the supervised broker executable: it serves the computer-use NDJSON pipe, walks UIA trees, captures frames, and injects input — the killable native side of the ComputerUse ACL.

## Domains

Each concern is owned by exactly one bounded context. When adding code, first ask which domain owns the concern — if the answer is "more than one" or "none", the boundaries need attention before code is written.

- **Agent Domain**: the core agent loop, conversation orchestration, tool dispatch, execution flow, and sub-agent spawning/runtime.
 A per-session watchdog (`AgentWatchdog`, application layer; pure policy in the Agent Domain) re-homed on supervisor events: each tick (default 60 s) it iterates the `ChildSupervisorRegistry` — one `ChildSupervisor` per running child, fed by the supervisor event stream (`ChildEventStream`), no sweep-based discovery and no wall-clock child timeout (ChildTimeout was deleted; wall-clock is never a cancellation source). Cancellation sources are exactly three: explicit interrupt, a watchdog terminal decision, and the budget hard ceiling. Spawn-time capability grants (`tool.allow`/`tool.deny` on the persisted `SpawnContract`) are enforced at DISPATCH: the spawn command resolves the child's effective set from the parent's persisted resolution (or the session's child tool surface) and persists it, the child's loop registry is a `FilteredToolRegistry` and its exec capability registry a `FilteredCapabilityRegistry`; denied dispatches return the verbatim `Error [GrantViolation]: tool '<name>' is not granted to this agent.` and append a `GrantViolation` audit row. Grants are namespace-aware (issue #108): an entry ending in `.*` is a namespace pattern (`mcp.github.*`) whose dispatch root (`mcp`) rides the effective set so the dispatch tool resolves; a bare root allow inherits the parent's pattern reach (a child granted bare `mcp` reaches exactly the parent's reach); widening is measured over namespace reach (a pattern must nest within a parent pattern or a patternless root; an unexpressible deny subtraction is a spawn-validation error) — and the resolved entries ride the child's run as the ambient `McpGrantScope` (AsyncLocal, the anchor-scope pattern): the `mcp` tool re-checks the RESOLVED id (`mcp.<server>.<tool>`) at dispatch and filters the listing to reachable servers. Mid-run revocation is out of scope (ledgered ruling). **Root steering is a wire round trip, drained at a mid-stream safe point (issue #253).** A message a human types while a turn runs travels over the `root-steer` wire kind to the LIVE root turn and the HOST delivers it into the ROOT container's inbox — the box the root loop drains and the hub its waits subscribe to. The app's own container runs no agent work, so posting there queued the message where nothing drains: the model never saw it and no `agent.wait` ever woke, which is the defect this closed. The loop drains at turn entry, at iteration boundaries, and at a MID-STREAM safe point right after a no-tool answer lands in history, so a steer typed during a pure-text stream reaches the model in the SAME turn instead of waiting for a turn that may never come. The Desktop's echo renders PINNED below the streaming block until the loop's own `MailboxDrainedEvent` names that message, then reflows to its chronological position.

Out-of-process children ride `eThangAgent.ChildHost` + `eThangAgent.Transport.ACL` (always on — every conversation runs in its own host; see the Transport ACL row); the design record for the whole subsystem lives at state key `specs/2026-07-19-subagent-system`. Sessions ARE the domain's root agents: every turn persists its full message slice (user, assistant tool-call messages, tool results, nudges) losslessly through `IAgentStore`, CHILD runs persist INCREMENTALLY — the Agent subscribes to conversation mutations (`Conversation.Subscribe`) and flows every message through `IChildTranscriptStore`/`ChildTranscriptStore` to the store at the safe point it is added, always with `CancellationToken.None`, so an interrupt or crash leaves the run's transcript persisted up to the last safe point (the 2026-10-04 incident erased a 31-minute child because terminal persistence ran under the cancelled run token); terminal persistence (flush + terminal row) also runs under `CancellationToken.None`, and a persistence fault throws `TranscriptPersistException`, which the runtime catch-all reports honestly as `failed to persist child transcript` — never the misleading `A task was canceled.` —, and the host shell's **Sessions** menu (Desktop left-menu entry) lists persisted root sessions via the session catalog (`SessionCatalogQueryHandler`), newest first, greying out ones already open in a tab. The catalog lists only RESUMABLE rows: a depth-0 record whose bound provider this build no longer knows (e.g. a session persisted under the retired z.ai provider) is omitted — resume would fail `UnknownProvider`, so the dead entry is never offered. The gate is the optional `isResumableProvider` predicate wired to `Providers.IsKnown` at the composition root, keeping provider identity out of the domain, and `Providers.DisplayName` renders an unknown id as its raw text instead of throwing, so a display surface never crashes on historical data. Confirming a row resumes that session by id — the factory rebuilds the container on the session's ORIGINAL provider and workspace and hydrates the conversation from the persisted transcript, so the conversation continues where it stopped. Opening a workspace always mints a NEW session — resume is manual via the menu, never automatic for a directory. `AgentRecord`'s workspace/provider columns are discovery metadata only: they never scope conversation content, and unrelated sessions in one workspace share nothing conversational (only the deliberately workspace-scoped durable stores — state keys, plan records, picker preferences, consented links — carry across a workspace's sessions). The agent loop carries two optional collaborators wired via `AgentOptions`: `IContextMonitor` (per-provider-call usage accounting), `IContextCompactor` (model-driven voluntary cleanup is the primary mechanism and the compactor is the backstop; the compaction pressures derive per window from `CompactionPolicy` — a pure sliding table over the resolved window size, ceiling/soft-reminder/target running from ~80/70/40% under 200K tokens through 70/60/35% and 60/50/30% to 50/40/25% at 1M+ — never from a model name and never from configuration (`AgentOptions.CompactionThreshold` is deleted; zero config), re-derived per iteration so a mid-session window change re-derives automatically. At the policy's soft level the loop appends a ONE-TIME System reminder naming the pressure, the `context_trim` tool, and the ceiling — it never repeats until a successful compaction or context shrink resets the pressure cycle. At the ceiling the compactor runs its deep clean: eviction plans to the policy's target with a protected head — every message through and including the FIRST user message (system messages, prior compaction summaries, the original task statement) is never evicted — the evicted exchange groups are replaced by an LLM handoff summary, and the kept tail's oversized tool results (over 5% of the window budget) then compress to deterministic relocation markers (`ToolResultMarker.For` names what produced the result and how to re-fetch it) oldest-first until the tail fits the target; when eviction cannot free enough (tail-dominated bloat), that tail compression IS the lever and succeeds without a summarizer call. The trigger distrusts a provider-reported input-token count far beyond the conversation's own character estimate (server-side tool calls ride the provider's accounting without entering the history — firing on them fails spuriously with CompactionImpossible). A compacted root turn persists by transcript replacement, not the append slice. The same compactor also recovers in-loop from a context-window overflow: the OpenRouter ACL maps an HTTP 400 whose body names the context-length fault to the distinct `ContextWindowExceeded` error code (other 400s stay `ProviderError`), and the loop answers that code with one forced compaction and one retry — a second overflow, a compaction failure, or no wired compactor fails the turn (`CompactionUnavailable` when nothing is wired), never a silent loop. The model can also shrink its own context at a milestone: the `context_edit` tool (Tool Domain, over the `IConversationContextService` port adapted from the Conversation Domain's `ConversationContextService`) renders the indexed message list and removes/shortens selections through `Conversation.Compact`'s protocol invariants, and its `context_trim` sibling tool trims or shortens TOOL RESULTS only (a tool-only selection guard), replacing them with the same relocation markers; a successful shrink returns the verbatim `[context: shrank ...]` sentinel, which the loop reads to rest auto-compaction for the turn and (root and child alike) switch persistence to whole-transcript replacement (`TurnCallbacks.OnContextShrunk` carries the signal to hosts). Static context-hygiene guidance (the `ContextHygienePromptProvider`, composed into every session's system prompt) tells the model to trim served tool results with `context_trim` as it works — clean at task milestones, keep concrete identifiers — riding root and children alike. **The request prefix is frozen once per turn (issue #267).** The system prompt and the tool definitions are the LEADING bytes of every request, so a value that changes between iterations invalidates the provider's prompt cache from its first changed character — every later token re-billed at full input price, silently. `Agent.RunTurnAsync` therefore snapshots both into a `RequestPrefix` at the turn's start and reuses it for every iteration (the loop previously called `_systemPrompt.Build()` at three sites and read `_tools.Definitions` at two, all inside the loop). The turn boundary is the deliberate seam: content that legitimately changes mid-session (a skill installed while the user works) takes effect on the NEXT turn — a cache miss the user asked for — instead of on an arbitrary iteration. `ISystemPromptProvider.Build()` carries a PURITY CONTRACT (identical output for identical state, no state-changing I/O, never a timestamp or counter), and `SessionFilesPromptProvider` — which used to re-read every configured session file on every `Build()` while its doc claimed purity — now snapshots its reads at CONSTRUCTION. The trim cost is visible rather than invisible: every tool-result shrink's sentinel appends `[cost: ~N tokens saved, ~M re-billed from the rewrite point]` (`ContextShrinkCost`, deterministic character estimates at the documented 4-chars-per-token rate), because a prefix cache re-bills everything from the first rewritten message onward and the relocation markers are worth that price only when someone can see it. Measured baseline (2026-10-24, this workspace's `agent_events` usage rows, 182 provider calls): 97.67% cache-hit rate overall; 4 of 176 growing iterations invalidated the cache, 312,750 tokens total — 1.49% of all input tokens, worst single event 174,208 tokens — so mid-array rewrites are rare and the prefix is otherwise stable. No fix in this audit changes request bytes. The reasoning channel is TELEMETRY, never context (issue #263, parent #261): reasoning deltas accumulate into `ModelResponse.Reasoning` (nullable — a provider that streams none stays null, never an empty string, and the non-streaming parser accumulates the same trace from a `reasoning` output item, preferring the raw `reasoning_text` parts over the provider's `summary`), and the loop records one `AgentReasoningRecorded` event per iteration through `IAgentEventLog` (implemented by `SqliteAgentStore` over the existing append-only `agent_events` table — no schema change, `type = "reasoning"`, identity = agent + turn id + 0-based iteration) at the safe point where the response exists, with `CancellationToken.None`, so an interrupt leaves every completed iteration's trace persisted and a store fault is SWALLOWED (best-effort, never turn-failing). Nothing reads it back: `ResponsesApiRequestCore.BuildInput` has no path to the event log, which is what makes the model's next request byte-identical whether or not a trace was persisted (pinned by test on both sides), and the display channel is unchanged — the same fragments still stream to `OnReasoningDelta`. Children record under their own agent id. Each provider call also records a `usage` row on the same table and identity (agent + turn + iteration, issue #270) carrying the provider-scored `InputTokens`/`OutputTokens` and the nullable `CachedInputTokens`/`ReasoningTokens` — NULL when unreported, never a fabricated zero — so the reasoning-in-context family's measurements (reasoning tokens per step, cache-hit rate) are computable from the database with a plain `SELECT`; like the trace it carries no price (per-call cost remains the usage ledger's) and nothing reads it back into a request. Absent collaborators mean byte-identical legacy behavior. Server-side tool calls the provider executes inside its own response (web_search, web_fetch, image generation) never enter the message history, so the loop SURFACES them: one System line per call (`[<tool>] <detail>`, each result URL beneath) that also lands in the conversation so a resumed session sees it. An `openrouter:image_generation` call's artifact is PERSISTED first (issue #230): the wire carries it under `result`/`imageUrl` as a `data:<media>;base64,<payload>` URL (never under `action`, where the search/fetch detail lives), `ServerToolCallImage` carries it provider-neutrally (media type + payload), and the loop writes the bytes into the workspace through the Tool Domain's `IServerToolImageStore` seam — `.ethang/images/` under the session workspace, or under a child's ANCHOR when it has one, because a generated image belongs beside the work that produced it. The surfaced line then NAMES the saved path, and the image rides the `OnToolResult` callback so the Desktop renders it through the same surface computer screenshots already use. The store SNIFFS the format from the decoded bytes rather than trusting the wire's media-type claim, bounds size by `ImageLimits.MaxBytes`, and refuses anything but PNG/JPEG; every refusal is a typed error ON THE LINE, never a silent skip. RECORDED DESIGN DECISION — the artifact reaches the MODEL as a path, not as an inlined image part: the Responses API's `Message` input shape accepts `input_image` only on user/system/developer roles (an assistant message cannot carry one, so relaxing `Conversation.NormalizeParts` would emit a wire shape the provider rejects), a synthetic tool result is unattributable (`function_call_output` needs a `call_id` from a `function_call` item), and inlining a 1024x1024 PNG costs 1.3-2.7 M base64 characters re-sent on every later request. The path costs a dozen tokens and `read_image` pulls the bytes on demand, so the line names the path and — gated on `ModelConfig.AcceptsImageInput`, so a text-only model is never invited to call a tool that would fail — says `read_image` can open it.

- **Model Domain**: model capabilities, provider contracts, model configuration, and model+provider resolution (`IModelCatalog`, `RootAgentResolver`, `SessionModelPreferences`). Context accounting lives here too: both ACLs report provider-scored `TokenUsage` on every response, `ModelConfig` carries a nullable `ContextWindow` — null means not yet catalog-resolved (bootstrap configs); every serving model's window resolves from the provider catalog through `IContextWindowSource` (no curated constants exist; OpenRouter's `openrouter/auto` is a fetched catalog row at its API-reported size), and a catalog miss fails the turn/spawn loudly (never a fabricated window), and `ContextAccountant` (`IContextMonitor`) keeps utilization against that window — provider usage reports are the only decision input; character-based numbers are estimates for UI breakdowns only. Both ride the `context` wire payload as defaulted members (an older host's omission reads as unreported) so the CTX line's `, cache 82%, reasoning 1.2K` segments advance in a host-run session, and a provider reporting neither renders exactly the pre-#262 line. The harness never substitutes a different model: the user picked `minimax/minimax-m3.1-flash:free` and the turns ran on `openrouter/auto` (2026-10-22) — a silent substitution is a lie about what ran. The Desktop therefore always NAMES the session's model (the user's persisted pick, else the session's pin — the record of what actually served, so a resume continues with it — else the session's default), so the status bar and the model that serves are the same model, and the live choice RIDES the root-turn request (`RootTurnRequest.ModelPreferences`, opaque JSON decoded host-side) because the picker lives in the app while the conversation's agent lives in the host process — a choice that did not travel never reached the model that served. There is no automatic model selection: the former smart-selection and measured-mix reselection features were removed (the `IModelSelector` seam, `SmartModelSelector`, `SmartSelectionOptions`, `ModelSelectionResult`, `MeasuredMixPolicy`, `MeasuredMixPrior`, and the `DynamicReselectionCoordinator` were deleted). The persisted `ModelUsed` pin is the record of what actually served — resume stability and the status bar read it — and is re-pinned only when the user picks a model; the fallback id and `AgentRecord.UnassignedModel` count as unpinned. The Desktop's Model Settings window carries the **Model** section (a searchable catalog list; the standalone model/effort rail entries are gone — grand-plan item 117); the choice lands in `SessionModelPreferences` and applies from the next turn, root and children alike, and the Desktop persists it per workspace + provider so reopening a directory restores it. There is no configured model pin — model choice is runtime-only. `SessionModelPreferences` carries runtime-adjustable knobs — reasoning effort and model, both via the Model Settings window, plus TWELVE provider-neutral sampling knobs (top-p, top-k, frequency/presence/repetition penalties, min-p, top-a, seed, verbosity, parallel-tool-calls, and the temperature and max-tokens caps) set through the Model Settings window. Every knob is a nullable runtime preference: a null knob is OMITTED from the request body so the provider default applies — true for the ten nullable sampling knobs, while temperature and max-tokens are non-nullable on `ModelConfig` and always travel (a null preference there means the app-resolved default, not an omitted key). The `ModelPreferencesOverlay` overlay carries them onto every resolved config (root and children alike); OpenRouter-only request settings (provider routing, the ten server tools available on the responses API (openrouter:subagent was removed as an option — its server-side agent loop cannot complete inside the request timeout, and the harness owns subagents natively), plugins, loop budgets) are typed in the OpenRouter ACL (`OpenRouterRequestSettings`) and travel as OPAQUE JSON in `ProviderSettings` — domain code never interprets them —. The effort choice — model default or one of seven levels — maps to OpenRouter's unified `reasoning.effort` and is persisted + restored per workspace + provider. The **Reasoning summary (display)** selector beside it is the parent #261 display channel (#264): a nullable `ReasoningSummaryLevel` (`Auto | Concise | Detailed`) on `OpenRouterRequestSettings`, carried in the same opaque `ProviderSettings` payload and emitted as `reasoning.summary` beside `effort` — the two knobs are INDEPENDENT, so either can be set alone and the `reasoning` object is emitted whenever either is (neither set omits the key entirely). It is display-only by construction: it changes what the provider streams into the transcript and never the request's `input` array (pinned by test on both the ACL and the E2E path), because the harness asks the provider for its own summary rather than writing a summarizer or asking the model to narrate its thinking.

- **Memory Domain**: recall and search over persisted sessions (lexical and bounded-regex query planning). The former curated-memory learning loop was removed (issue #236); the project keeps only the recall machinery behind the `memory` provider.
- **Skill Domain**: the methodology-skill subsystem — three skill sources under one contract. Embedded built-in skills ship verbatim (`EmbeddedSkillCatalog` over SKILL.md resources in the Skill Domain assembly, including the using-skills session contract and the ethang-tools-mapping tool-binding skill); file skills load from user-configured directories in agentskills.io format (each immediate subdirectory holding a SKILL.md, or a SKILL.md at the directory root, is one skill — everything else in the folder is ignored); learned skills are agent-created, with version history and usage tracking. The `CompositeSkillCatalog` merges built-ins and file skills with precedence built-in > global-directory > workspace-directory — a file skill never shadows a built-in, and later same-name entries are shadowed with a `[collision]` diagnostic — while learned resolution falls through to the store only after a catalog miss. Frontmatter parsing (`SkillMarkdown`) demands `name` and a non-empty `description`; the honored agentskills.io keys are `metadata.version` (integer) and `disable-model-invocation` (a manual skill); known-but-unapplied keys (`allowed-tools`, `license`, `compatibility`) and unknown keys load with per-file warnings — warnings never fail a load, and one bad file degrades to a diagnostic, never a whole-load failure. Manual skills never appear in the always-on listing, carry a `[manual]` marker in `skill_list`, and load by name. Skill directories are host configuration: the `skill_directories:global` / `skill_directories:ws:{root}` preference keys (the same `{path, enabled}` JSON shape as the session-file lists), edited in the Desktop's Open Workspace dialog (moved out of the Settings window); nothing configured means no file skills. Every session (root, children, and remote — the ChildHost resolves the same directories from the settings it serializes via `AgentComposition.ResolveSkillDirectoriesFromSettings`) carries the `SkillsListingPromptProvider`'s budgeted listing: 8,000 characters total, descriptions truncated at 60 characters, grouped Built-in / Global directory skills / Workspace directory skills / Learned, `[collision]`/`[warning]` lines rendered, and a truncation marker whenever any description or entry was dropped — never silent. The session bootstrap (`SkillsBootstrapPromptProvider`) injects the using-skills contract verbatim — prefer a matching skill over improvising, announce it, load its body with `skill_view`, the user's instructions outrank skills — with no emphasis wrapper; the development-methodology skills are description-triggered from the listing, not session defaults. The tools: `skill_list` (builtin/file/learned source labels, the `[manual]` marker, catalog diagnostics), `skill_view` (the origin directory in the annotation for file skills; usage rows recorded for learned views only), `skill_manage` (refuses to create a name held by a built-in or file skill — `NameCollision` — and reports `BuiltInImmutable`/`SkillNotFound` on update or delete of either); the skill registry tools (`skill_search`, `skill_registry` install/update/uninstall with a deterministic BLOCK/advisory content scan and the `skill_registry:default_target` preference) install community skills into configured directories, surfacing same-session through hot reload — which is live in the container that actually serves the model: `AgentComposition.StartSkillHotReload` is called at BOTH container build sites (`AgentSessionFactory.BuildContainer` and `SessionHost.Create`), because production turns run in the ChildHost process and an app-side-only start left every real session's watcher inert, so a skill added mid-session stayed invisible for the session's whole lifetime (issue #269). The reload announcement reaches the transcript through the container's `SessionNoticeSink` carrier — the sink the shell binds at attach — never through a DI-resolved `AgentSession`, which is registered in no container. Deterministic user invocation (spec #28, superseding skill-routing spec #19 decision 6's gated user-invocation channel) runs through ONE application core: `SkillInvocationService` resolves a name case-insensitively over the full visible+manual catalog (0 hits -> `SkillNotFound`, >1 -> `AmbiguousSkill` listing the matches) and renders the verbatim `[skill invoked: <name>]` System line — description truncated at the 60-character budget, body inlined, a >4,000-character body falls back to a `skill_view` pointer (`SkipReason=oversize`), arguments ride a final `arguments:` line, and NO `skill_usage` row is written (view-hygiene rule). The channels: the `skill_invoke` tool (returns the one-line confirmation, never the body) and the Desktop's `/` slash input — a raw-first-character `/` (no trim) opens the `SkillAutocompleteViewModel` popup (manual skills first, case-insensitive substring filter over the name token, wrap-around navigation, Tab/Enter accept autofills `/<full name> `); at submit, a found name injects the System line then forwards the full input as the ordinary user message, an unknown name stays a plain message, and an ambiguous name sends nothing and surfaces a transcript notice listing the matches. A headless activation eval (`tools/SkillActivationEval` — `ETHANG_EVAL_KEY`, `ETHANG_EVAL_PROMPT_BUDGET_SECONDS`, `ETHANG_EVAL_LOCAL_BASE_URL`; deliberately not part of the solution) drives real sessions over `prompts.json` to measure skill activation, with before/after results captured as plan records.

## Project Structure

The solution follows a layered DDD structure. Each bounded context has its own project with:

- `Domain` — aggregates, entities, value objects, domain events, specifications, repository interfaces
- `Application` — commands, queries, handlers, application services
- `Infrastructure` — repository implementations, ACL implementations, external service adapters
- `Contracts` — public interfaces, DTOs, and contracts shared across boundaries (kept minimal)

Shared kernel (cross-cutting concerns shared across domains):

- `SharedKernel` — base types, common value objects, guard clauses, result types

ACLs live in an `ACL` project each, implementing domain-owned interfaces.

### Naming Conventions

- Domain namespaces omit the dot: `eThangAgent.ToolDomain`, `eThangAgent.ConversationDomain`.
- ACL namespaces keep it: `eThangAgent.OpenRouter.ACL`, `eThangAgent.FileSystem.ACL`.

## Development Conventions

- **No shell intermediary**: repo automation is plain `dotnet` CLI invocations; do not commit `.ps1`/`.sh`/`.cmd`/`.bat` scripts. If a task needs scripting, prefer C# (the same language as the codebase).

- **Build**: `dotnet build`.
- **Formatting & analyzer severity**: enforced mechanically — `.editorconfig`, `Directory.Build.props`, and the CI lint job are the source of truth; this document deliberately does not restate their rules. Apply with `dotnet format whitespace eThangAgent.slnx` before committing (apply analyzer fixes only per rule, never in bulk — `dotnet format` without a subcommand also applies semantic analyzer fixes and can rewrite signatures), then verify with the exact CI lint gate before pushing: `dotnet format eThangAgent.slnx --verify-no-changes --severity warn`. That verify command is a strict superset of the whitespace subcommand — it also runs style and third-party analyzers (the JSON001–005 family, e.g. `Probable JSON string detected`), which never surface on `dotnet build` even with `EnforceCodeStyleInBuild` + `TreatWarningsAsErrors`, because the family executes only in the format/IDE host and not the batch compiler; the verify run is their only automated net. (The signature-rewrite hazard is apply-direction only — `--verify-no-changes` writes nothing.) Sonar rules (SXXXX) are enforced at build time via `SonarAnalyzer.CSharp` (referenced in `Directory.Build.props`), mirroring the SonarQube Cloud profile: a finding must surface on `dotnet build`, not only after push. xUnit rules (xUXXX) are enforced at build time via `xunit.analyzers` (pinned in `tests/Directory.Build.props`; xunit.v3 3.2.x already pulls ≥ 1.27.0 transitively, so the pin exists to take 2.0.0's rule set ahead of the xunit.v3 4.x bump, which requires ≥ 2.0.0 and therefore conflicts with nothing). Named deviations live in `.editorconfig` (S1135, S125 off — their heuristics collide with this repo's prose) or targeted `#pragma warning` pairs at by-design sites (deliberate empty base records, provider base-URL constants, best-effort cleanup catches). Two carve-outs are named decisions, not leniency: CA1707 (xUnit `Method_Scenario_Expected` names) is suppressed in test projects only; CA2007 (`ConfigureAwait`) is suppressed in `eThangAgent.Desktop` only, because the UI SynchronizationContext is load-bearing — view-model continuations must resume on the UI thread. In test projects, awaits of same-assembly tasks use `ConfigureAwait(true)` in xUnit test methods and `ConfigureAwait(false)` in fake/helper classes (xUnit1030 forbids `false` in test methods).
- **Testing**: xUnit. Three layers: unit, integration, and E2E tests. Solution-level `dotnet test eThangAgent.slnx` runs every test project concurrently (Microsoft.Testing.Platform: one testhost per project, up to `Environment.ProcessorCount` modules at once); on a loaded machine the timing-sensitive integration tests (named pipes, git worktrees, Roslyn shell kills) can contend — pass `--max-parallel-test-modules <n>` (e.g. 4) to bound the concurrency. There is NO desktop-driving computer-use test suite: the owned-window integration tests were removed deliberately (they popped real windows and raced the user's own desktop use); computer-use coverage is stub-host supervision tests, wire/contract tests, and the fake-access E2E — nothing creates windows or injects input on the user's desktop. Aim for 100% coverage; minimum 80% required. Unit tests use fakes only — a domain test must never know PowerShell, HTTP, or OpenRouter exist. Integration tests exercise real ACL implementations against real files / sandbox endpoints. E2E tests drive the desktop app headless — real composition behind the view-model — against a local mock provider server. Test selection runs on the xunit.v3 / Microsoft.Testing.Platform runner, not VSTest: `dotnet test --filter` is rejected (exit 5, help dump) — use `--filter-class` (fully-qualified class name), `--filter-method`, `--filter-trait`, or `--filter-query`; the runner also rejects `--no-build` and `--nologo` (exit 5, help dump) — plain `dotnet test <project> --filter-class <FQN>` is the working form; exit 2 means failures, exit 8 means zero tests matched.
- **Session retrospective**: at the end of every session/task, evaluate how *the agent itself* handled the session — bugs in its behavior, gaps in its tool surface, missing skills or workflow support — and include that evaluation in the summary to the user rather than letting it evaporate. The retrospective evaluates and targets the harness itself — a general agent that can be used on any repository, in any language, for multiple users — never the host repo: suggestions must target the agent (new tools, capabilities, prompts, reliability), never one-off fixes baked into a specific repo. A pattern that recurs across sessions or repos is a signal to promote it into a first-class agent capability. The retrospective also reports the session's loop telemetry in one fixed line — hypotheses stated, predictions tested, refuted count, skips recorded — read from the plan's `sci.<slug>/ledger` through the `experiment` tool; the records ARE the telemetry, so there is no second store.
- **Deadlock vigilance in tests**: a test that can wait forever eventually will. Any test exercising an unbounded or externally-settled await (channels, gates, `TaskCompletionSource`) must have a reachable completion path under the code under test's *current* contract — before running the suite, trace what settles the await. When a contract changes from bounded to unbounded, update every test that relied on the old bound in the same change, asserting the new contract directly rather than scripting the old one. A hung test blocks the whole suite and the agent itself; after fixing the cause, kill the orphaned `testhost` process before rerunning.
- **Every change leaves the build green**: a task is not done if the solution does not build and all tests pass.
- **Green includes a clean tree**: a task is not done while `git status --porcelain` shows output. Intended changes are committed; unintended ones are reverted or surfaced. Uncommitted work is unfinished work.
- **Dependency injection**: all wiring at the composition root — the host-agnostic `eThangAgent.Composition` library (`AgentComposition`/`AgentSessionFactory`), consumed by the Desktop host. Domains depend only on interfaces and contain zero DI container references.
- **Immutability**: domain models prefer immutability — records, init-only properties, copy constructors.
- **Error handling**: result types, not exceptions, for expected domain failures. Exceptions are for infrastructure/programmer errors.
- **Tool design**: tools demand strictly correct input (see Guiding Philosophy). Tool errors are returned to the model as tool results — an error is feedback for self-correction, never a turn-ending crash. The loop's `ToolRepeatGuard` guards three loop shapes — two failure-fed and one success-fed. Identical-args nudges at the 2nd/5th identical failure, plus a cross-argument breaker that counts consecutive failures of one tool across ANY arguments, nudges at the 3rd and SUSPENDS the tool at the 13th (3+10) — the loop then refuses further calls with `Error [ToolSuspended]` without executing them (2026-10-04: ~200 varied failed exec calls never re-tripped the identical-args nudges). The success-repetition breaker (2026-10-08: a depth-1 subagent re-ran one identical exec call 235 times over 2.5 hours, every call returning the same 2843-char payload — invisible to a guard fed only by `isError`) counts consecutive byte-identical SUCCESSFUL calls of one tool, nudges at the 3rd and SUSPENDS at the 13th, mirroring the failure breaker; a failure, a different tool, or different arguments resets it, so legitimate polling is not punished. The loop keys both identical-args streaks on the tool's SEMANTIC call identity, not raw arguments (issue #124, 2026-10-15: the model varied exec's `title` envelope field every call, resetting the streaks 195 times over one identical call) — a tool declaring `IToolCallIdentifiable` (exec: the program body) feeds its identity to the guard; envelope fields the model free-varies (`title`, `timeoutSeconds`) can no longer reset a streak. Model-facing output uses explicit format contracts (annotation lines, gutters) documented verbatim in the tool description, so the model never has to guess what it is looking at.
- **Performance**: hot paths (file reads, shell execution) go through in-process hosting where possible; avoid per-call process spawns. Streaming over loading: read only the requested range, then account for the whole. Aim for event-driven flow over polling loops, and keep steady-state memory small — don't hold what you're not using. Maintain high performance, low latency, low memory, and a modular event-driven architecture across every change.
- **Create tools as you work**: when something useful is missing, add a tool for it rather than working around the gap. Tools are the agent's first-class surface — a missing capability is a missing tool, not a one-off script. New tools follow the existing `ITool` / capability-provider contracts: strict input validation, `Result<T>` errors, and verbatim format contracts in the description.
- **Prefer tools over exec scripts**: the Roslyn `exec` engine is for one-off glue, not a substitute for first-class capabilities. When the model keeps writing the same or similar scripts across sessions — repeated file probing, shell-out patterns, query shapes — that is a signal to promote the pattern into a general tool with proper validation and format contracts. The model should spend its effort on decisions, not on re-deriving boilerplate C#.
